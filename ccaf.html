From knowing to scoring — the elimination method

This exam is not a memory test. Nearly every question describes a production system misbehaving and asks for the best fix. Convert knowledge into marks with one repeatable triad:

  1. Name the root cause — tool ordering? tool selection? decomposition? escalation boundary? attention dilution? error reporting? context loss?
  2. Match the guarantee level — must hold every time (money, identity, safety) → programmatic. Should hold usually → prompt + few-shot.

The Claude Certified Architect – Foundations credential validates that you can make sound, tradeoff-aware decisions when designing and building real applications with Claude. The Four Pillars

One mental model for the four technologies — and the single most important distinction on the whole exam: workflows versus agents.

1.1The big picture — workflows vs. agents

Anthropic draws a clean line between two kinds of "agentic systems": Workflows orchestrate LLMs and tools through predefined code paths — you decide the steps; the model fills blanks but never chooses the route. Agents let the model dynamically direct its own process and tool usage — you give a goal and tools; it decides what to do next, in what order, and when it's done.

In plain terms

A workflow is a railway — fixed tracks, predictable stops. An agent is a car with a destination — it picks the roads itself.

Why the distinction matters: the right architecture depends on how predictable the task is. If you can predict the steps ("summarize → translate → format"), a workflow is simpler, cheaper, more reliable, easier to debug. If you can't ("research this open-ended topic", "fix whatever breaks the tests"), an agent's flexibility is worth its higher cost and compounding-error risk.

The five composable patterns (Building Effective Agents)

① Simplest

Prompt chaining

A fixed sequence; each step's output feeds the next. For predictable multi-stage tasks (outline → draft → polish).

②

Routing

Classify the input, send to a specialized handler. Separates concerns so one prompt needn't be good at everything.

③

Parallelization

Concurrent work in two flavors — sectioning (independent subtasks) and voting (same task several times, aggregate). For speed or cross-checking.

④

Orchestrator–workers

A central model dynamically decomposes, delegates to workers, synthesizes. Key difference from parallelization: subtasks aren't known in advance. Foundation of the research scenario.

⑤ Most autonomous

Evaluator–optimizer

One model generates; another evaluates and gives feedback; loop until good enough. When you have clear criteria and iteration adds measurable value.

Three principles + meta-rule

Simplicity · Transparency · ACI

Maintain simplicity; show the model's planning steps; carefully craft the agent–computer interface (tool docs & testing). Meta-rule: start simple, add agentic complexity only when simpler solutions fall short.

⚠ Exam trap

A predictable multi-step task (a review that always analyzes files then checks integration) → fixed / prompt-chaining decomposition, not a fully autonomous agent. Open-ended investigation → dynamic decomposition wins. Match the pattern to the predictability of the task.

1.2The Claude API and the agentic loop

The core endpoint is Messages: you send alternating user/assistant messages, optionally a system prompt, tool definitions, and parameters like max_tokens. The single most important field for agents is stop_reason — why Claude stopped generating this turn.

stop_reason — the values you must know
ValueMeaningLoop action
tool_useClaude wants to call one or more toolsExecute the tool(s), append results, continue
end_turnClaude finished naturallyStop — present the final response
max_tokensOutput token limit hit before finishingHandle truncation
refusalClaude declined the requestStop; don't retry to force compliance
 
THE AGENTIC LOOP — control flow is driven by stop_reason

   ┌─────────────────────────────┐
   │  Send conversation → Claude │◄────────────────────┐
   └──────────────┬──────────────┘                     │
                  ▼                                    │
        ┌──────────────────┐      tool_use   ┌─────────┴──────────┐
        │   stop_reason ?  ├────────────────►│ Execute tool(s) &  │
        └────────┬─────────┘                 │ append tool_result │
                 │ end_turn                  └────────────────────┘
                 ▼
        ┌──────────────────┐
        │  STOP — return   │     (max_tokens / refusal also end it)
        │  final response  │
        └──────────────────┘

Two facts the exam tests repeatedly: ① tool results are appended to the conversation history so the model can reason about what to do next — the loop is "stateful" only because you keep resending the growing message list. ② which tool to call next is model-driven — Claude reasons; you don't hard-code a decision tree (unless you specifically need deterministic ordering — see Domain 1.4).

★ Remember

Continue the loop while stop_reason == "tool_use". Terminate when stop_reason == "end_turn". This is the canonical, correct control flow.

⚠ Exam trap — three anti-patterns

Never decide when to stop by (a) parsing natural-language text for words like "done", (b) an arbitrary iteration cap as the primary stopping mechanism (caps are fine as a safety limit only), or (c) checking whether the response contains assistant text — Claude often emits text alongside tool calls. The real signal is always end_turn.

Tool use and tool_choice

tool_choice valueBehavior
"auto"Claude decides — call a tool or reply with text. Default when tools are provided.
"any"Claude must call some tool, but chooses which. Guarantees a tool call — no free-form text.
{"type":"tool","name":"X"}Claude is forced to call the specific tool X.
"none"Claude may not call any tool. Default when no tools are provided. (Exam outline emphasizes the first three; know all four.)
Why it matters

tool_choice is the lever for guaranteed structured output. Forcing a specific extraction tool means Claude cannot wander into prose — it must produce arguments matching that tool's schema. Full treatment in Domain 4.

1.3The Claude Agent SDK

The Claude Agent SDK (formerly the Claude Code SDK; Python & TypeScript) runs Claude Code's autonomous loop inside your own process. The crucial contrast: with the base API / Client SDK, you implement the tool loop — the while stop_reason == "tool_use" code. With the Agent SDK, Claude handles the loop: call something like query(prompt=...) and iterate a stream of messages while the SDK reads files, runs commands, calls tools, and repeats until done.

Built-in tools the SDK ships (same ones powering Claude Code)
CategoryToolsPurpose
File operationsRead, Edit, WriteRead, modify, create files
SearchGlob, GrepFind files by pattern; search contents with regex
ExecutionBashShell commands, scripts, git
WebWebSearch, WebFetchSearch the web; fetch & parse pages
DiscoveryToolSearchLoad tools on demand instead of preloading all schemas
OrchestrationAgent (a.k.a. Task), Skill, AskUserQuestion, task-trackingSpawn subagents, invoke skills, ask the user, track tasks

Key building blocks

  • AgentDefinition — a subagent's configuration: its description, prompt (system prompt), allowed tools, and optionally model and reasoning effort. How you define a specialized worker.
  • The Task/Agent tool — how a coordinator spawns subagents. The coordinator's allowed tools must include Task (current SDKs surface it as Agent in tool-use blocks but still reference Task internally — check both names).
  • Hooks — callbacks at specific loop points (before/after a tool, on finish…). They run in your process and can intercept, modify, or block actions — deterministic control. (Domain 1.5.)
  • Sessions — every run has a session ID you can capture to resume later or fork into a parallel branch.
  • Permissions & limits — allowed_tools auto-approve tools; permission_mode governs the rest; max_turns and max_budget_usd cap a run; effort controls reasoning depth.
In plain terms

The base API is a manual transmission — you shift gears in the loop. The Agent SDK is automatic — Claude shifts for you. Both go the same places; you choose how much you want to drive.

1.4Claude Code

Claude Code runs in the terminal, in IDEs (VS Code, JetBrains), a desktop app, on the web, and on mobile. Under the hood it uses the same agent loop as the SDK — the Agent SDK is "Claude Code as a library." For the exam, it appears as configuration and workflow features you must know how to use and where to put.

CLAUDE.md files — the project's always-on memory

A CLAUDE.md is plain Markdown that Claude Code loads automatically into context at the start of every session, before you type anything: coding conventions, the architecture in a paragraph, how to run build/tests, libraries to prefer or avoid, review expectations. Its power is the hierarchy — multiple files layer from broad to specific:

CLAUDE.md HIERARCHY — more specific / managed layers override broader ones

  ┌───────────────────────────────────────────────┐  ▲ higher
  │ MANAGED   enterprise / org policy             │  │ precedence
  ├───────────────────────────────────────────────┤  │ (wins on
  │ DIRECTORY subfolder/CLAUDE.md   · shared      │  │  conflict)
  ├───────────────────────────────────────────────┤  │
  │ PROJECT   .claude/CLAUDE.md or root CLAUDE.md │  │
  │           team standards · committed/shared   │  │
  ├───────────────────────────────────────────────┤  │
  │ USER      ~/.claude/CLAUDE.md                 │  │
  │           personal defaults · NOT shared      │  │
  └───────────────────────────────────────────────┘

When several apply, the more specific scope wins / layers on top (roughly: managed → project → user). Keep files modular with @import — a small root CLAUDE.md importing per-package standards only where relevant. (Current versions add an enterprise-managed policy layer and machine-local overrides.)

Why it matters — classic exam diagnostic

"A teammate reports Claude is ignoring the team's standards" → the rules were placed at user scope (personal, unshared) instead of project scope. Remember the split: project = shared/committed; user = personal/uncommitted.

.claude/rules/ — modular, path-scoped conventions

Instead of one ever-growing CLAUDE.md, break conventions into topic files (testing.md, api-error-handling.md). Each can carry YAML frontmatter with a paths glob, so it loads only when you're editing matching files:

---
paths: ["**/*.test.*"]
---
Use Arrange–Act–Assert. Mock network calls. One behavior per test.

Because matching is by glob, ["**/*.test.*"] follows test files wherever they live. That's the right tool when conventions attach to a kind of file scattered across directories — something a single root CLAUDE.md (relies on inference) and per-directory CLAUDE.md (directory-bound) both handle poorly. It also saves tokens: a rule enters the prompt only when relevant.

Slash commands and skills — reusable workflows

Package a repeatable task once, trigger as /command-name (optionally with arguments). Historically: Markdown in .claude/commands/ (project, shared) or ~/.claude/commands/ (user, personal). These have now converged with skills — the recommended format is a folder at .claude/skills/<name>/SKILL.md bundling instructions plus helper scripts. Frontmatter that controls behavior:

  • description — when the skill should be used (how Claude decides to invoke it).
  • context: fork — run in an isolated sub-agent so verbose output never pollutes the main conversation; only the result comes back.
  • allowed-tools — restrict which tools the skill may use (e.g. read-only), preventing destructive actions.
  • argument-hint — prompt the user for an argument when invoked without one.
★ The distinction the exam draws

Skills are on-demand and task-specific (loaded only when invoked); CLAUDE.md is always-loaded universal context. Skill = a procedure you run sometimes. CLAUDE.md = standards that always apply.

Plan mode — explore and propose before touching code

In plan mode Claude works read-only: it investigates, reasons about an approach, and presents a step-by-step plan for approval before editing a single file — preventing the expensive failure where the agent confidently makes dozens of wrong changes you must unwind. Use it when complexity is already evident: large/multi-file changes, several valid approaches, architectural decisions (new service boundaries). For a small well-scoped fix — a single-file bug with a clear stack trace — direct execution is faster; plan mode is just ceremony. Plan mode often pairs with an Explore subagent that absorbs noisy discovery and returns a concise summary, protecting your main context budget.

⚠ Exam trap

When requirements already describe architectural or multi-approach complexity → choose plan mode now. Don't pick "start direct and switch to planning later if it gets complicated."

MCP integration — connecting Claude Code to your systems

  • .mcp.json — project-scoped, committed, shared. Use ${VAR} env-var expansion (e.g. ${GITHUB_TOKEN}) so secrets are referenced, never hard-coded.
  • ~/.claude.json — user-scoped, for personal/experimental servers.
  • When a server connects, all its tools become available at once (discovered at connection time). Shared + personal servers can be active in the same session.
  • Write rich MCP tool descriptions, or Claude may default to a generic built-in (like Grep) instead of your more capable MCP tool.

Memory and context commands — keep long sessions healthy

  • /memory — inspect (and edit) which memory files are loaded; diagnose why a convention is or isn't followed.
  • /compact — compress the conversation into a summary, freeing space while keeping key facts. (Claude Code also compacts automatically, inserting a compaction boundary.)
  • /clear — reset when starting something genuinely unrelated.
Why it matters

Over a long run, models drift toward "typical" patterns and lose specifics discovered earlier. Compaction, scratchpad notes, and subagent isolation are the standard defenses (Domain 5).

CLI flags — driving Claude Code from scripts and CI

  • -p / --print — headless mode: take the prompt, run, print to stdout, exit. Essential in CI, where an interactive prompt would hang the job forever.
  • --output-format json — machine-parseable output so a pipeline can act programmatically (e.g. inline PR comments).
  • --json-schema — constrain that output to a schema you define.
  • --append-system-prompt — add run-specific instructions ("only flag security issues").
  • --resume / --continue — let automation pick up a prior named session.
⚠ Exam trap

A CI job that "hangs forever" is the tell-tale sign you forgot -p / --print. Invented flags such as CLAUDE_HEADLESS or --batch are common distractors.

1.5The Model Context Protocol (MCP)

MCP is an open standard (created at Anthropic, announced November 2024) for connecting AI applications to external data and tools — one protocol instead of bespoke integrations. Think universal adapter — "USB-C for AI tools." Architecture: a client–server model over JSON-RPC 2.0. Hosts are the apps the user touches (Claude Desktop, an IDE, Claude Code, your agent); clients live inside the host, each holding a 1:1 connection to one server — the external program exposing capabilities.

1.6How the pieces fit together

  • The Claude API is the engine: messages in, responses out, tool use governed by stop_reason and tool_choice.
  • The Agent SDK wraps that engine in a ready-made loop with built-in tools, subagents, hooks, sessions, permissions — agents without hand-writing the loop.
  • Claude Code is the same engine and loop delivered as a developer tool — configured via CLAUDE.md, rules, skills, plan mode, MCP.
  • MCP is how all of the above reach your systems and data in one standard, reusable way.

The exam constantly asks you to choose the right layer for a problem: a prompt fix vs. a hook, a description tweak vs. a new tool, plan mode vs. direct execution, the synchronous API vs. the Batch API. The chapters ahead train exactly that judgment.

Agentic Architecture & Orchestration

The largest domain: how agents run (the loop), how multiple agents cooperate (orchestration), and how to make critical steps reliable (enforcement, hooks, sessions). The recurring theme — prefer model-driven flexibility where appropriate, but use programmatic mechanisms when correctness is non-negotiable.

2.1Designing agentic loops · Task 1.1

The lifecycle: send a request → inspect stop_reason → if tool_use, run the tools and append their results → repeat → stop on end_turn. Each pass that includes tool calls is one turn; a simple question may take one, a complex task can chain dozens. The loop works because tool results are written back into history — Claude doesn't "remember" outputs by magic; your code appends each result as a message and resends the growing list. That's how new information enters its reasoning.

Model-driven vs. pre-configured decisions

Model-driven — Claude looks at context and decides which tool to call. The default agentic style; right when the path depends on what's discovered. Pre-configured — you hard-code a decision tree or fixed sequence. Appropriate only when the order is genuinely fixed and must be guaranteed (and even then you usually enforce it with code, not the loop itself — §2.4).

⚠ The three anti-patterns, restated
  1. Parsing natural-language signals ("the model said 'finished', so I'll stop"). Models produce text in many contexts — unreliable.
  2. Arbitrary iteration caps as the primary stopping mechanism. A cap is a safety net, not the completion logic.
  3. Checking for assistant text content as a completion indicator. Presence of text ≠ task done — Claude often emits text alongside tool calls.

The correct, robust signal is always stop_reason == "end_turn".

2.2Coordinator–subagent orchestration · Task 1.2

When one agent can't hold an entire complex task in its head, split work across a coordinator (orchestrator) and subagents (workers) — the orchestrator–workers pattern realized as hub-and-spoke.

HUB-AND-SPOKE — all traffic flows through the coordinator

   Web search ─────┐  ✕ no direct  ┌───── Document analysis
    subagent       │  subagent ↔   │         subagent
                   ▼  subagent     ▼
              ┌─────────────────────────┐
              │       COORDINATOR       │   delegate ►  ◄ final result
              └─────────────────────────┘
                   ▲               ▲
    Synthesis ─────┘               └───── Report generation
    subagent                              subagent
   (each subagent has ISOLATED context — only its final result returns)

What the coordinator does

  • Decomposes the overall task into subtasks.
  • Delegates each subtask to the right subagent.
  • Routes all inter-subagent communication through itself — subagents talk to the coordinator, never each other.
  • Aggregates results.
  • Decides which subagents to invoke based on the query's complexity — never blindly running the full pipeline every time.
★ The most-tested fact in this domain

Subagents run with isolated context. A subagent does not inherit the coordinator's conversation history. Each starts fresh (it does load its own system prompt and project context like CLAUDE.md), does its focused job, and returns only its final result. The coordinator's context grows by that compact result — not the subagent's whole transcript — which is exactly why subagents are such powerful context management.

Why hub-and-spoke?

Routing everything through the coordinator gives observability (one place to watch), consistent error handling, and controlled information flow. Direct subagent-to-subagent chatter loses all three.

Risks — and how to manage them

  • Overly narrow decomposition — the coordinator carves a broad topic into too-narrow pieces, and whole areas vanish. (The famous "creative industries" question: the coordinator generated only visual-arts subtasks and missed music, writing, film.)
  • Duplication — overlapping subagents waste effort. Partition the scope: each gets a distinct subtopic or source type.
  • Insufficient coverage — build iterative refinement loops: the coordinator evaluates synthesis for gaps, re-delegates targeted queries, re-runs synthesis until coverage suffices. (Evaluator–optimizer applied to research.)
⚠ Exam trap

When a multi-agent system "succeeds" at every step but produces incomplete output — suspect the coordinator's decomposition, not the downstream agents. If each subagent did its assigned job, the problem is what they were assigned.

2.3Subagent invocation, context passing & spawning · Task 1.3

Spawning subagents

  • Spawned via the Task tool (current SDKs may surface it as Agent). A coordinator's allowedTools must include "Task" — omit it and the coordinator cannot delegate at all. Omit Task from a subagent's own tools: subagents cannot spawn their own subagents.
  • An AgentDefinition configures each type: description (matches tasks to the agent), prompt (system prompt), tools (restricted toolset), plus optional model and effort.
  • Parallel: the coordinator emits multiple Task calls in a single response — not one per turn across turns. Parallel spawning turns a minutes-long sequential pipeline into a seconds-long concurrent one.
  • Fork-based session management branches from a shared analysis baseline to explore divergent approaches (e.g. compare two refactoring strategies). See §2.7.

Passing context — the part people get wrong

Because subagents don't inherit parent context, you must pass everything they need explicitly in their prompt: put complete findings from prior agents directly in the subagent's prompt (hand the synthesis subagent the actual web-search results and document-analysis outputs); and use structured formats that separate content from metadata (source URLs, document names, page numbers) so attribution survives the move between agents.

Designing coordinator prompts

Specify research goals and quality criteria, not rigid step-by-step procedures. Goal-oriented prompts let subagents adapt; over-specified procedural prompts make them brittle.

★ Remember

Subagents are amnesiacs by design — they know only their system prompt, their project context, and whatever you put in this invocation's prompt. "It will just remember what the coordinator found" is always wrong.

2.4Multi-step workflows — enforcement & handoffs · Task 1.4

One of the exam's central tensions: prompt-based guidance ("always verify identity first" in the system prompt) is probabilistic — it works most of the time with a non-zero failure rate. Programmatic enforcement (hooks, prerequisite gates) is deterministic — code that blocks an action guarantees the rule, every time.

★ The decision rule

When a business rule requires guaranteed compliance — anything with financial, legal, or safety consequences — use programmatic enforcement, not a prompt.

Prerequisite gates

A gate blocks a downstream tool until an upstream step completes. Canonical example: block process_refund until get_customer has returned a verified customer ID. A prompt instruction will occasionally be skipped; a gate cannot be.

Decomposing multi-concern requests

"My order is late, I was double-charged, and I want to change my address" — decompose into distinct items, investigate each (often in parallel, sharing context), then synthesize one unified resolution — rather than tackling only the first issue or producing three disjointed replies.

Structured handoff protocols

When escalating mid-process, the human usually cannot see the transcript. Compile a structured handoff: customer ID, root-cause analysis, relevant amounts (e.g. refund amount), recommended action — so they act immediately instead of re-investigating.

⚠ Exam trap

"The agent sometimes skips a required step" → the answer is almost always a programmatic prerequisite/gate, not "improve the prompt" or "add few-shot examples." Prompts reduce the failure rate; they don't eliminate it. (Worked Question 1.)

2.5Agent SDK hooks — interception & normalization · Task 1.5

Hooks are callbacks at defined loop points. They run in your application process — not in the model's context window — so they're deterministic and consume zero tokens.

Two flagship uses for the exam

  1. PostToolUse for data normalization. Different MCP tools return different shapes — Unix timestamps here, ISO 8601 there, numeric status codes elsewhere. Why it matters — the deciding principle

A prompt that says "never refund more than $500" will eventually let a $501 refund through. A PreToolUse hook that checks the amount and blocks it will not. Hooks for deterministic guarantees; prompts only for probabilistic guidance. The exam rewards recognizing when you've crossed from "nice to have" into "must be guaranteed."

2.6Task decomposition strategies · Task 1.6

The core choice: fixed sequential pipelines (prompt chaining) for predictable, multi-aspect work — e.g. a code review that (1) analyzes each file individually then (2) runs a separate cross-file integration pass — versus dynamic adaptive decomposition for open-ended investigation — e.g. "add comprehensive tests to a legacy codebase": map the structure, identify high-impact areas, build a prioritized plan that adapts as dependencies surface.

Key technique — splitting reviews to avoid attention dilution

Reviewing many files at once spreads attention thin: some files get deep feedback, others superficial; bugs are missed; feedback turns contradictory (a pattern flagged in one file is approved in another). The fix: per-file local analysis passes + a separate cross-file integration pass. Each file gets focused attention; integration issues get their own dedicated pass.

⚠ Exam trap

For inconsistent results on a large multi-file review → split into focused passes — not "use a bigger context window" (doesn't fix attention quality), not "make developers split the PR," not "run three passes and require 2-of-3 consensus" (suppresses real bugs caught only intermittently). (Worked Question 12.)

2.7Session state, resumption & forking · Task 1.7

  • Named session resumption — --resume <session-name> continues a specific prior conversation, restoring its full context (files read, analysis done, actions taken).
  • fork_session — an independent branch from a shared baseline to explore divergent approaches without disturbing the original (compare two testing strategies from one codebase analysis).
  • Starting fresh with a structured summary — sometimes the cleaner choice.

Resume vs. start fresh

Resume when prior context is mostly still valid. Start fresh with an injected summary when prior tool results are stale — after files changed, cached file contents in the old session are now wrong; a new session seeded with a structured summary of the relevant facts is more reliable. If you do resume after code changes, tell the agent exactly which files changed so it re-analyzes only those rather than re-exploring everything.

★ Remember

Stale tool results are a trap. If the world moved on since the session was captured, prefer a fresh session with a clean structured summary over resuming with outdated data. Forking is for parallel exploration, not for recovering from staleness.

Tool Design & MCP Integration

Tools are the contract between a deterministic system (your code) and a non-deterministic agent (Claude). Unlike APIs built for human developers, agent tools must assume the caller might misread, misuse, or hallucinate.

3.1Effective tool interfaces · Task 2.1

Descriptions are the steering wheel

Tool descriptions are the primary mechanism Claude uses to choose a tool. Minimal descriptions = unreliable selection. A good description includes: the tool's purpose and when to use it (and when not to); input formats it accepts, with example queries; and edge cases & boundaries — explicitly how it differs from similar tools. Anthropic's own engineering found that even small description refinements yield dramatic accuracy improvements — treat description-writing as real engineering, not documentation.

The overlap problem

Two near-identical descriptions cause misrouting: analyze_content vs. analyze_document both described as "analyzes things" — Claude can't tell them apart. Fixes: rename and re-describe to remove overlap (e.g. analyze_content → extract_web_results with a web-specific description), or split a generic tool into purpose-specific tools with defined contracts (analyze_document → extract_data_points, summarize_content, verify_claim_against_source).

Naming and parameters — Anthropic's tool-design guidance

  • Namespace/prefix related tools so their domain is clear.
  • Unambiguous parameter names: prefer user_id over user (a name? an object? an ID?).
  • Return meaningful, human-readable context rather than opaque technical IDs.
  • Prefer search-style tools (search_contacts) over list-everything tools (list_contacts); manage token volume with pagination, filtering, truncation.

Watch the system prompt

Tool selection is keyword-sensitive. System-prompt wording can create associations that override even well-written descriptions (a prompt that keeps saying "document" nudges Claude toward the document tool inappropriately). When diagnosing misrouting, review the system prompt for keyword bias, not just the descriptions.

⚠ Exam trap

Two similar tools confused, both with minimal descriptions → the best first step is to expand the descriptions (inputs, examples, edge cases, boundaries) — low effort, high leverage. Few-shot adds token overhead without fixing the root cause; a routing layer is over-engineering; consolidation is valid but heavier than a "first step." (Worked Question 2.)

3.2Structured error responses for MCP tools · Task 2.2

When a tool fails, how it tells the agent determines whether the agent can recover intelligently. MCP signals failure with isError — but the flag alone isn't enough.

Error categories — the right reaction differs
CategoryMeaningRight reaction
TransientTimeout; service temporarily unavailableRetry (often locally)
ValidationInvalid inputFix the input; don't blindly retry
BusinessPolicy violation (refund over limit)Do not retry; explain to the user / escalate
PermissionNot authorizedDo not retry; needs different handling

Why uniform errors are harmful: a generic "Operation failed" tells the agent nothing — it can't decide whether to retry, fix input, or give up, so it wastes retries on non-retryable failures or abandons recoverable ones. A good error response contains: an errorCategory (transient / validation / business / permission), an isRetryable boolean (or retriable: false for business-rule violations), and a human-readable description — for business errors, a customer-friendly explanation so the agent can communicate appropriately.

Local recovery and partial results

  • Subagents should recover locally from transient failures and propagate to the coordinator only errors they cannot resolve — including what was attempted and any partial results.
  • Distinguish access failures from valid empty results. A timeout (access failure) needs a retry decision; "the query ran fine and found zero matches" is a success with no data. Conflating them leads to bad recovery.
★ Remember

Structured, categorized, retryable-tagged errors let the agent make smart recovery decisions. Generic failures blind it. This idea returns in Domain 5.3 — error propagation across agents.

3.3Distributing tools & configuring tool choice · Task 2.3

Fewer tools, better selection

Too many tools degrades selection reliability — an agent with 18 tools makes worse choices than one with 4–5, because every extra tool raises decision complexity. And agents handed tools outside their specialization misuse them (a synthesis agent with web-search tools starts doing searches it should delegate). The principle: scoped tool access — give each agent only what its role needs, plus a few limited cross-role tools for specific high-frequency needs.

Concrete moves

  • Restrict each subagent's toolset to its role to prevent cross-specialization misuse.
  • Replace generic tools with constrained alternatives — e.g. replace fetch_url with load_document that validates document URLs.
  • Scoped cross-role tools for common needs — give the synthesis agent a narrow verify_fact for simple lookups while complex verification still routes through the coordinator. Least privilege: satisfy the common case cheaply, keep the existing pattern for the hard case. (Worked Question 9.)

tool_choice for control flow

  • Forced selection ({"type":"tool","name":"…"}) guarantees a specific tool runs first — e.g. force extract_metadata before enrichment tools — then handle later steps in follow-up turns.
  • "any" guarantees the model calls some tool rather than returning conversational text.
⚠ Exam trap

A specialized agent strays into another agent's job → scope its tools (optionally add one narrow cross-role tool for the frequent simple case) — not "give it the full toolset of the other agent." Over-provisioning violates separation of concerns.

3.4Integrating MCP servers · Task 2.4

  • Project-level servers → .mcp.json at the repo root: shared with the team via version control — the right place for tooling everyone needs.
  • User-level servers → ~/.claude.json: personal/experimental, not shared.
  • Credentials without committing secrets — .mcp.json supports environment-variable expansion: reference ${GITHUB_TOKEN} so the token is read at runtime and never committed.
  • Discovery — all configured servers' tools are discovered at connection time and become available simultaneously (hence the "too many tools" caution in §3.3).
  • Resources expose content catalogs — issue summaries, documentation hierarchies, DB schemas — giving the agent visibility so it can skip exploratory tool calls. Resources = context/data; tools = actions.
  • Making MCP tools win over built-ins — Claude sometimes prefers a built-in (Grep) over a more capable MCP tool. Fix: enhance the MCP tool's description so the agent understands it's the better choice.
  • Build vs. reuse — prefer existing community servers for standard integrations (e.g. Jira); reserve custom servers for team-specific workflows. Don't rebuild what exists.
★ Remember the file map

.mcp.json = project, shared, version-controlled. ~/.claude.json = user, personal. ${VAR} expansion for secrets. Resources = catalogs/context; tools = actions.

4.1CLAUDE.md — hierarchy, scoping, modularity · Task 3.1

  • User-level — ~/.claude/CLAUDE.md. All your projects, your machine only. Not shared via version control.
  • Project-level — .claude/CLAUDE.md or a root CLAUDE.md. Committed and shared with everyone who clones.
  • Directory-level — a CLAUDE.md inside a subdirectory, scoped to that part of the tree.

Current Claude Code is richer — an enterprise-managed policy layer and a machine-local CLAUDE.local.md also exist; precedence runs roughly managed > local > project > user. The rule to memorize: more specific instructions win over broader ones. User says "2-space indent," project says "4-space" → the project rule wins inside that project.

Modular organization

  • @import — reference external files (@docs/coding-standards.md). Imports resolve relative to the file containing them, can nest (to a depth limit), and trigger an approval prompt the first time they pull from an external location. Use them to include only the standards relevant to each package.
  • .claude/rules/ — split topics into focused files (testing.md, api-conventions.md, deployment.md), picked up automatically alongside CLAUDE.md.

Diagnosing problems

New teammate missing the instructions → they were at user level (personal, not shared); move them to project scope. Use /memory to see which memory files are loaded and diagnose inconsistent behavior — if an instruction "disappeared," it may have been given only in conversation, or lives in a nested CLAUDE.md that hasn't reloaded.

⚠ Exam trap

"Why didn't my teammate get this rule?" → user-level config isn't version-controlled. Shared rules go in project-level CLAUDE.md (or .claude/rules/). When levels conflict, the more specific level wins.

Current reality

4.4Plan mode vs. direct execution · Task 3.4

Choose plan mode

Explore read-only, design first

Large-scale changes & multi-file modifications · multiple valid approaches & architectural decisions · when committing to the wrong approach is costly to undo. Examples: microservice restructuring, a library migration touching 45+ files, choosing between integration approaches with different infrastructure requirements.

Choose direct execution

Simple, well-scoped, clear path

A single-file bug fix with a clear stack trace; adding one validation conditional. Planning here is just overhead.

The Explore subagent isolates verbose discovery output during plan mode (and other discovery-heavy phases) and returns a summary — preventing context-window exhaustion in multi-phase tasks. A common correct pattern: plan first, then execute — plan mode to investigate and design (a library migration), then direct execution to implement the chosen plan.

⚠ Exam trap

Requirements already state large scale + architectural decisions ("restructure the monolith into microservices across dozens of files") → enter plan mode now — not "start direct and switch if it gets complex" (complexity is already known), not "direct with comprehensive upfront instructions" (you don't yet know the right structure). 4.5Iterative refinement techniques · Task 3.5

  • Concrete input/output examples. The single most effective way to communicate an expected transformation — when prose descriptions are interpreted inconsistently, provide 2–3 concrete input→output pairs.
  • Test-driven iteration. Write a test suite first (expected behavior, edge cases, performance), then iterate by sharing test failures with Claude to guide progressive fixes.
  • The interview pattern. Have Claude ask you questions to surface considerations you didn't anticipate (cache-invalidation strategy, failure modes) before implementing — especially valuable in unfamiliar domains.
  • One message vs. sequential. All issues in a single detailed message when fixes interact (Claude reconciles them together); fix sequentially when problems are independent.
Why it matters

"Be more accurate" rarely helps. Two correct examples, or a failing test, communicates the standard far more precisely than adjectives. The exam favors concrete examples and tests over vague exhortations.

4.6Claude Code in CI/CD · Task 3.6

  • -p / --print — non-interactive: process prompt, print to stdout, exit. Prevents the classic CI failure of a job hanging on interactive input.
  • --output-format json with --json-schema — structured, machine-parseable findings a pipeline can post as inline PR comments.
  • CLAUDE.md provides CI context — testing standards, fixture conventions, review criteria. Documenting these improves test-generation quality and reduces low-value output.
  • No duplicates: re-running reviews after new commits → include prior findings in context and instruct Claude to report only new or still-unaddressed issues. Test generation → provide existing test files so Claude doesn't duplicate covered scenarios.
  • Session isolation matters — the same session that generated code is less effective at reviewing its own changes than an independent review instance (it carries its generation reasoning and is biased toward its own decisions). Recurring reliability theme — see Domain 4.6.

Part Five · Domain 4 · 20% of the exam

Prompt Engineering & Structured Output

Reliable, well-shaped output: precise criteria, few-shot examples, JSON schemas, validation loops, batch processing, and multi-pass review. The unifying idea — be specific and show, don't just tell, and use the API mechanism that guarantees what you need rather than hoping a prompt achieves it.

5.1Explicit criteria → precision, fewer false positives · Task 4.1

Vague instructions ("check that comments are accurate") produce vague behavior. Explicit, categorical criteria ("flag a comment only when the claimed behavior contradicts the actual code behavior") produce precise behavior. The difference is the gap between an opinion and a rule.

  • General hedges do not help. "Be conservative" or "only report high-confidence findings" does not reduce false positives the way specific categorical criteria do — the model's self-reported confidence is poorly calibrated, so leaning on it backfires.
  • Why false positives are so costly: high false-positive categories undermine trust in the accurate ones. If a code-review bot cries wolf in one category, developers start ignoring all its findings — including the correct ones. Protecting precision is protecting adoption.
  • Write specific review criteria defining which issues to report (bugs, security) vs. skip (minor style, local patterns) — not confidence-based filtering.
  • Temporarily disable a high-false-positive category to restore developer trust while you improve its prompt.
  • Explicit severity criteria with concrete code examples per level for consistent classification.
⚠ Exam trap

To fix poor precision, choose explicit categorical criteria (with examples) — not "tell it to be conservative," not "raise the confidence threshold." Specificity is the lever; confidence-based filtering is not.

5.2Few-shot prompting for consistency & quality · Task 4.2

Few-shot (multishot) prompting — a few worked examples in the prompt — is the most effective technique for consistent, actionable output when detailed instructions alone fall short. Anthropic's guidance: include 3–5 diverse, relevant, clear examples, wrapped in <example> tags (nested in <examples> when there are several). More good examples generally means better performance.

Benefit 1

Demonstrate format

Location, issue, severity, suggested fix — output becomes consistent because the shape was shown, not described.

Benefit 2

Ambiguous-case judgment

Show the reasoning for why one choice was made over a plausible alternative — which tool for an ambiguous request, how to judge a branch-level coverage gap.

Benefit 3

Generalization

Done well, examples teach judgment that transfers to novel patterns rather than matching only the exact cases shown.

Benefit 4

Less hallucination in extraction

Examples covering varied document structures (inline citations vs. bibliographies, narrative vs. tables) cut down empty/null or fabricated fields.

  • Create 2–4 targeted examples for ambiguous scenarios that show the reasoning for the chosen action.
  • Include examples that distinguish acceptable patterns from genuine issues — reduces false positives while still generalizing.
  • Use examples to demonstrate varied document formats to fix empty/null extraction of required fields.
Remember

The exam repeatedly frames few-shot as the right answer for format consistency, ambiguous-case judgment, and false-positive reduction — with one critical exception from 1.4: when a rule must be guaranteed (financial gates), few-shot is not enough; you need programmatic enforcement.

This eliminates JSON syntax errors — output is constrained to the schema's shape.

Syntax errors vs. semantic errors — a subtle, testable distinction

Strict schemas eliminate syntax errors but not semantic errors. The output will be valid JSON of the right shape, but it can still be wrong: line items that don't sum to the stated total, a value placed in the wrong field, a fabricated number. Schemas guarantee structure, not correctness.

  • Required vs. optional/nullable. Make a field optional/nullable when the source may not contain it — this prevents the model from fabricating a value just to satisfy a required field.
  • Enums with an escape hatch. Enum fields plus an "other" value with a detail string for extensible categories, and an "unclear" value for genuinely ambiguous cases.
  • Normalization rules in the prompt. Pair a strict output schema with format-normalization instructions to handle inconsistent source formatting.
Remember

5.4Validation, retry & feedback loops · Task 4.4

Schemas catch syntax problems; validation catches semantic ones.

  • Retry-with-error-feedback. On a validation failure, send a follow-up request containing the original document, the failed extraction, and the specific validation error(s) — guiding the model to correct itself.
  • Know retry's limits. Retries work for format mismatches and structural errors. They are useless when the required information is simply absent from the source — no amount of retrying conjures data that isn't there. Recognizing "the info exists only in an external document we didn't provide" saves wasted calls.

Designing self-correcting validation

  • Extract calculated_total alongside stated_total so a mismatch is automatically flagged.
  • Add a conflict_detected boolean for inconsistent source data.
  • Add a detected_pattern field to findings so you can analyze which code constructs trigger findings — enabling systematic study of false-positive/dismissal patterns when developers reject findings.
⚠ Exam trap

Distinguish semantic validation errors (values don't sum, wrong field) from schema syntax errors (already eliminated by tool use). And remember: retries fix format/structure problems, not missing-information problems.

5.6Multi-instance & multi-pass review architectures · Task 4.6

  • Self-review is weak. A model that generated something retains its reasoning context and is less likely to question its own decisions in the same session.   • Multi-pass review. For large reviews, split into per-file local-analysis passes plus separate cross-file integration passes (the same attention-dilution fix from Domain 1.6). Avoids superficial coverage and contradictory findings.
  • Calibrated review routing. Run verification passes where the model reports confidence alongside each finding — then route the low-confidence/ambiguous ones to humans.

Part Six · Domain 5 · 15% of the exam

Context Management & Reliability

Keeping systems accurate and trustworthy over long, complex, multi-agent work: preserving the facts that matter, escalating wisely, propagating errors so the system can recover, surviving large-codebase exploration, routing the right cases to humans, and never losing track of where information came from.

6.1Preserve critical information across long interactions · Task 5.1

The two failure modes

  • Progressive summarization risk. As a long conversation is repeatedly summarized to save space, precise facts get blurred — numbers, percentages, dates, customer-stated expectations turn into vague phrases. The $47.50 refund the customer was promised becomes "a refund."
  • "Lost in the middle." Models reliably attend to information at the beginning and end of a long input but may drop findings from the middle. Where you place information affects whether it is used.
  • Tool-result bloat. Tool results accumulate and consume tokens disproportionately to their relevance — an order lookup might return 40+ fields when only 5 matter, and those 40 fields sit in context forever.

The techniques

  • Persistent "case facts" block. Extract transactional facts (amounts, dates, order numbers, statuses) into a persistent facts block included in every prompt, outside the summarized history — so they never get blurred away. For multi-issue sessions, keep a separate structured layer of issue data.
  • Trim verbose tool outputs to only the relevant fields before they accumulate (keep just the return-relevant fields from an order lookup).
  • Position-aware ordering. Put key-findings summaries at the beginning of aggregated inputs and organize details under explicit section headers to mitigate lost-in-the-middle.
  • Structured outputs from subagents. Require metadata (dates, source locations, methodological context) and structured data (key facts, citations, relevance scores) instead of verbose prose when downstream agents have limited context budgets.
  • Resend complete history in subsequent API requests — the API is stateless; conversational coherence is your job.
Remember

Don't let critical numbers ride inside summarized history. Pull them into a persistent, always-included facts block. Trim fat tool outputs early. Put the important stuff at the top and bottom.

6.2Escalation & ambiguity resolution · Task 5.2

Escalate when

Three valid triggers

① The customer explicitly asks for a human. ② A policy exception or gap — the policy doesn't cover the request (not merely that the case is "complex"). ③ Inability to make meaningful progress.

Never escalate on

Unreliable proxies

Not because a case seems hard or the customer sounds upset. Sentiment-based escalation and self-reported confidence are unreliable — the model is often confidently wrong on hard cases, so its confidence cannot gate escalation.

The nuances the exam tests

  • Honor an explicit human request immediately — do not first attempt your own investigation.
  • But when the issue is straightforward and within capability, acknowledge any frustration and offer to resolve it, escalating only if the customer reiterates the preference for a human.
  • Escalate on policy gaps — e.g. the customer wants competitor price-matching but policy only addresses own-site adjustments. The policy is silent → escalate.
  • Multiple matches require clarification. If a tool returns several possible customer matches, ask for additional identifiers — never pick one by heuristic.
  • How to implement: explicit escalation criteria with few-shot examples in the system prompt showing when to escalate vs. resolve.
⚠ Exam trap

The fix for poor escalation calibration is explicit criteria + few-shot examples — not self-reported confidence thresholds (poorly calibrated), not a separately trained classifier (over-engineered before prompt optimization is tried), and not sentiment analysis (sentiment ≠ complexity). (Worked Question 3.)

6.3Error propagation across multi-agent systems · Task 5.3

Domain 2.2's error principle applied across agents: when a subagent fails, the coordinator needs enough information to recover.

  • Good propagation: return structured error context — the failure type, what was attempted (the query), any partial results, and potential alternative approaches. The coordinator can then retry with a modified query, try an alternative, or proceed with partial results and annotate gaps.
  • Anti-pattern 1 — generic statuses ("search unavailable") hide valuable context and block informed decisions.
  • Anti-pattern 2 — silently suppressing errors (returning empty results marked as success) prevents any recovery and risks shipping incomplete output.
  • Anti-pattern 3 — terminating the entire workflow on a single failure throws away work when recovery could have succeeded.
  • Distinguish access failures from valid empty results so the coordinator reacts correctly.
  • Subagents recover locally from transient failures and only propagate what they cannot resolve — with attempts and partial results attached.
  • Structure synthesis output with coverage annotations — which findings are well-supported vs. which topic areas have gaps due to unavailable sources.
⚠ Exam trap

For a timed-out subagent, the best choice is structured error context to the coordinator — not a generic "unavailable" status (hides context), not "mark the empty result as success" (suppresses the failure), not "terminate the whole workflow" (over-reacts). (Worked Question 8.)

6.4Context in large-codebase exploration · Task 5.4

The degradation signal: in extended sessions, the model starts giving inconsistent answers and references "typical patterns" instead of the specific classes it discovered earlier. That's the tell — it has lost the concrete details.

  • Scratchpad files. Agents write key findings to a scratchpad and reference it for later questions — persisting knowledge across context boundaries.
  • Subagent delegation. Spawn subagents for specific questions ("find all test files," "trace the refund-flow dependencies") while the main agent keeps high-level coordination and stays lean.
  • Summarize-then-spawn. Summarize the key findings of one exploration phase before spawning subagents for the next, injecting the summary into their initial context.
  • Structured state persistence for crash recovery. Each agent exports its state to a known location; on resume, the coordinator loads a manifest and injects it into agent prompts — the system becomes recoverable.
  • /compact reduces context usage during extended exploration when context fills with verbose discovery output.
Remember

The cure for context degradation is externalizing memory — scratchpads, summaries injected into fresh contexts, subagents that absorb the verbose work, manifests for crash recovery. When the model starts speaking in generalities about your code, it has lost the specifics; reach for these tools.

6.5Human review workflows & confidence calibration · Task 5.5

Aggregate metrics lie. A headline "97% accurate" can mask poor performance on a specific document type or field — one segment sitting at 70% while the whole looks healthy. Validate accuracy by segment — per document type and per field — before automating high-confidence extractions.

  • Stratified random sampling. Sample high-confidence extractions in a stratified way to measure ongoing error rates and detect novel error patterns — keep watching even the cases you trust.
  • Field-level confidence, calibrated. Have the model output field-level confidence scores, then calibrate the review threshold using a labeled validation set. Calibration against ground truth is what makes confidence usable for routing — raw self-reported confidence is unreliable; calibration is the missing ingredient.
  • Route the risky ones to humans. Send low-confidence or ambiguous/contradictory extractions to human review, prioritizing limited reviewer capacity where it matters most.
Why it matters

"We hit 97% overall, let's automate" is a trap if one document type sits at 70%. Segment the accuracy, sample the trusted cases continuously, calibrate confidence against labeled data before pulling humans out of the loop.

6.6Provenance & uncertainty in multi-source synthesis · Task 5.6

  • Provenance gets lost in summarization. When findings are compressed without preserving claim-source mappings, attribution disappears. The fix: require structured claim-source mappings (source URLs, document names, relevant excerpts) that the synthesis agent must preserve and merge, not discard.
  • Conflicting statistics from credible sources → annotate with source attribution; never silently resolve by arbitrarily picking one value. Let the coordinator decide how to reconcile.
  • Temporal data must carry publication/collection dates so differences over time aren't misread as contradictions — two figures can both be correct for different years (think 2019 vs. 2024).
  • Structure reports to distinguish well-established findings from contested ones, preserving original source characterizations and methodological context.
  • Document analysis completes with conflicting values included and explicitly annotated, leaving reconciliation to the coordinator.
  • Render content types appropriately — financial data as tables, news as prose, technical findings as structured lists — rather than forcing one uniform format.
Remember

Never let a claim float free of its source. Carry URLs/excerpts/dates through every summarization step. Annotate conflicts and timestamps instead of resolving or hiding them. Distinguish "established" from "contested" in the final report.

Part Eight

Worked Questions & Test-Taking Strategy

Twelve questions mirroring the exam's format and difficulty. Decide your answer before revealing. Each explanation goes beyond "why the right answer is right" to why each distractor is tempting but wrong — because recognizing the trap is the skill the exam tests.

The mindset

Most questions follow a template: "Here is a production system misbehaving. What is the best fix?" Your job is to find the option that addresses the root cause with the least unnecessary complexity and the right level of guarantee.

A reliable decision procedure

  1. Identify the root cause.What is actually broken — tool ordering, tool selection, decomposition, escalation boundaries, attention dilution, error reporting, context loss? Many distractors fix a different problem.
  2. Match the guarantee level.Does the rule need to hold every time (money, safety, identity) or just usually? Guaranteed → programmatic (gate / hook / forced tool). Usually → prompt / few-shot.
  3. Prefer the proportionate fix.The exam rewards the simplest effective change. "Add a description," "add explicit criteria," "split the passes" usually beat "build a classifier," "add a routing layer," "switch models."
  4. Beware over-engineering distractors.Trained classifiers, ML pipelines, new routing layers, and bigger models are frequently wrong because a simpler prompt/config/tool change solves it.
  5. Distrust self-confidence and sentiment.Any option gating behavior on self-reported confidence or customer sentiment is almost always wrong — confidence is uncalibrated; sentiment ≠ complexity. Calibration against labeled data is the exception that makes confidence usable.
  6. Watch for "blame the wrong component."If every subagent/step succeeded but output is incomplete, the fault is upstream — the coordinator/decomposition, not the workers.
  7. Read the requirements literally.If complexity is already stated, choose plan mode now; if a step is required, enforce it programmatically. Don't defer to "switch later if needed."
Answer every question

There is no guessing penalty, and blanks count as wrong. Eliminate the clearly-wrong options and commit.

Lab 1

Build a Multi-Tool Agent with Escalation Logic

Reinforces: Domain 1 (Agentic Architecture), Domain 2 (Tool Design & MCP), Domain 5 (Reliability). Scenario 1 in miniature — and it touches the highest-weighted domain on the exam.

The five steps

  • ① Define 3–4 tools with carefully differentiated descriptions — get_customer, lookup_order, process_refund, escalate_to_human. Deliberately include two confusable tools; write thin descriptions first, watch the agent misroute, then expand with purpose, exact input format, an example query, and a "use this instead of X when…" clause — and watch it recover. (Question 2, lived.)
  • ② Implement the agentic loop on stop_reason — tool_use → run tools, append tool_result, loop; end_turn → stop. Don't parse prose for "I'm done," don't stop on text presence, don't use an iteration cap as the primary stop (a high cap as safety net is fine). Every one of those don'ts is a named anti-pattern in 2.1.
  • ③ Add structured error responses — errorCategory (transient/validation/business/permission), isRetryable, a human-readable message. Test: transient → retried; business (isRetryable: false) → never retried, explained or escalated; validation → input fixed and retried. Distinguish an access failure from a valid empty result.

  • The loop never hangs, never stops early — ends precisely on end_turn.
  • Transient errors retried; business errors explained, never retried.
  • The refund hook blocks over-threshold refunds 100% of the time; get_customer always runs first.
  • A three-part message yields a single answer addressing all three parts.

  • A tool returns {"results": []}. How does the agent tell "the search failed" apart from "the search worked and found nothing"?

Common mistakesTeam standards in ~/.claude/CLAUDE.md (never shared) · per-directory CLAUDE.md for scattered files · forgetting context: fork · hard-coded tokens in .mcp.json · plan mode for trivial fixes, direct execution for clearly architectural work.

Self-check

  • A teammate reports Claude ignores the team's testing rules. Name the two most likely configuration causes and how you'd confirm each.
  • Tests live next to their components throughout the tree. Why do glob path-rules beat both a root CLAUDE.md and per-directory CLAUDE.md files here?
  • A skill that explores the whole codebase keeps flooding your session. Which one frontmatter setting fixes it, and what does it do?
Lab 3

Build a Structured Data Extraction Pipeline

Reinforces: Domain 4 (Prompt Engineering & Structured Output), Domain 5 (Reliability). This is Scenario 6 — two full domains at once.

The five steps

  • ① An extraction tool with a careful schema — required vs. optional/nullable fields; an enum with "other" + detail string and "unclear" for ambiguity. Feed documents with absent fields; confirm null comes back instead of fabrication. Tool use + schema eliminates syntax errors; nullable fields stop invented data (5.3).
  • ② A validation-and-retry loop — semantic validation (do line items sum to the stated total? right fields?); on failure, resend the original document + failed extraction + the specific error. Track which failures retries fix: format/structure yes; information absent from the source never — retrying just burns tokens. Self-correction: calculated_total vs. stated_total, conflict_detected (5.4).
  • ③ Few-shot for format variety — 2–4 examples across structurally different documents (inline citations vs. bibliography, narrative vs. table, formal vs. informal). Show the reasoning in tricky examples so the model generalizes. Confirms previously-missed fields now extract (5.2).
  • ④ A batch strategy — ~100 documents through the Batches API, unique custom_id each; results return out of order; resubmit only failures, chunking oversized docs. Do the SLA arithmetic: a 24-hour window → what cadence guarantees 30-hour turnaround? Refine on a small sample first (5.5).
  • ⑤ Human-review routing with calibrated confidence — field-level confidence; route low-confidence/contradictory cases to review; measure accuracy by document type and by field; calibrate thresholds on a labeled validation set; stratified sampling of the high-confidence bucket catches novel errors hiding behind a good aggregate (6.5).

Success looks like

  • Absent fields come back null; the model doesn't invent values.
  • Retries fix format errors and are skipped when data is truly missing.
  • Failed batch items resubmitted by custom_id; oversized ones chunked.
  • Review routing driven by calibrated confidence, validated per type and field.
Common mistakesMarking optional fields required (invites fabrication) · assuming tool_use guarantees correctness (it guarantees shape) · retrying when info isn't in the source · trusting raw confidence without calibration · reporting only aggregate accuracy.

Self-check

  • Your schema marks discount_code required, and the model invents codes for documents that have none. What's the fix, and why does it work?
  • An extraction's line items don't sum to the total. Does tool_use with a strict schema catch this? Why or why not — and what would catch it?
  • Overall accuracy is 97%, but downstream users complain about invoices specifically. What measurement practice would have surfaced this before automation?
Lab 4

Design & Debug a Multi-Agent Research Pipeline

Reinforces: Domain 1 (Orchestration), Domain 2 (Tool Design), Domain 5 (Context, Provenance, Error Propagation). The capstone — Scenario 3 built for real; it pulls together more task statements than any other lab.

The five steps (+ bonus)

  • ① A coordinator that delegates with explicit context — coordinator + two subagents (web search, document analysis); allowedTools must include "Task" or it cannot delegate at all; pass each subagent its needed findings directly in the prompt — subagents never inherit history (2.3).
  • ② Parallel spawning — multiple Task calls in a single response; compare latency against one-per-turn (sequential with extra steps). Depth limit: subagents can't spawn subagents — only the top-level coordinator spawns.
  • ③ Structured output separating content from metadata — each finding as a record: claim, evidence excerpt, source (URL/document), publication_date. Verify synthesis preserves attribution when merging. Structured fields are what survive synthesis — and they cut context bloat (6.6, 6.1).
  • ④ Error propagation with partial results — simulate a web-search timeout; local recovery first; then structured error context (failure type, attempted query, partial results, alternatives). Confirm the coordinator proceeds with partial results and annotates coverage gaps — never crashes, never silently returns empty. Question 8, exactly (6.3).
  • ⑤ Conflicting sources in synthesis — two credible sources, different statistics: keep both values with attribution; separate well-established from contested; add publication dates so a temporal gap (2019 vs. 2024 figure) isn't mistaken for a contradiction; render financial data as tables, news as prose (6.6).
  • Bonus — recreate the "narrow decomposition" failure — broad topic, coordinator decomposes into only one sub-area; every subagent succeeds yet the report is incomplete. Fix at the coordinator level, then add iterative refinement: evaluate synthesis for gaps and re-delegate targeted queries until coverage suffices. (Question 7.)

Success looks like

  • Parallel Task calls measurably cut latency vs. sequential turns.
  • Every claim traces to a source; conflicts show both values.
  • A timeout yields partial results + a coverage-gap annotation — never a crash or silent empty.
  • A too-narrow run is diagnosed as a coordinator problem and fixed there.
Common mistakesOmitting "Task" from allowedTools · assuming subagents inherit context · summarizing away attribution before synthesis · generic errors, empty-as-success, terminate-on-one-failure · blaming downstream agents for a narrow decomposition.

10.3The "Recurring Right Answers" pattern library

Across the sample questions and task statements, a small set of principles is correct again and again. If a question maps to one of these, the answer almost always follows the pattern. Memorize them; recognize them under exam pressure.

1
For must-hold rules, enforce in code — not the prompt.

Money, identity, safety, required ordering → hook, prerequisite gate, or forced tool. Prompts have a non-zero failure rate; the stronger-worded prompt is a tempting wrong answer. (Q1)

2
Fix tool selection at the description first.

Misrouting among similar tools → richer descriptions (purpose, inputs, examples, boundaries) before few-shot, routing layers, or consolidation. (Q2)

3
Fix decision boundaries with explicit criteria + few-shot.

Escalation miscalibration, false positives, inconsistent classification → categorical criteria + boundary-demonstrating examples — before any ML/classifier. (Q3)

4
Distrust self-confidence and sentiment.

Gating behavior on confidence scores or sentiment is almost always wrong — confidence is uncalibrated, sentiment ≠ complexity. Exception: confidence calibrated against labeled data. (Q3, 6.5)

5
All workers succeed, output incomplete → blame the coordinator.

Incomplete coverage with healthy subagents = too-narrow decomposition upstream, not downstream failure. (Q7)

6
Propagate errors as structured context with partial results.

Failure type + attempted action + partial results + alternatives. Never generic, never empty-as-success, never kill the workflow on one failure. (Q8)

7
Least privilege; narrow scoped tools for the common case.

A scoped tool for the frequent simple case (verify_fact for the 85%), coordinator routing for the rare complex case. (Q9)

8
Project scope = shared; user scope = personal.

Team-wide commands, standards, MCP servers → project (.claude/…, .mcp.json, committed). Personal → ~/.claude/…, ~/.claude.json. (Q4)

9
Scattered-by-type conventions → glob path rules.

.claude/rules/ with paths: globs beats monolithic CLAUDE.md (inference) and per-directory CLAUDE.md (directory-bound). (Q6)

10
Pick plan mode when complexity is already stated.

Architectural / multi-file / multi-approach work → plan mode now, not "start direct, switch later." Simple, clear scope → direct. (Q5)

11
In CI, run non-interactively with -p.

Hanging CI job waiting for input → add -p / --print. CLAUDE_HEADLESS, --batch, stdin redirection are wrong or non-existent. (Q10)

12
Match the API to the latency need.

Batch (cheap, ≤24h, no SLA, no in-request tools) for overnight/bulk; synchronous for blocking checks. Never batch what developers wait on. (Q11)

13
Split big reviews into per-file + integration passes.

Inconsistent multi-file review = attention dilution. Focused passes fix it; a bigger context window does not. (Q12)

14
tool_use guarantees shape, not correctness.

Strict schemas eliminate syntax errors; semantic errors (sums, field placement) still need validation + retry. (5.3–5.4)

15
Nullable fields stop fabrication.

If the source may lack a field, mark it nullable so the model returns null instead of inventing. Add "other"/"unclear" enums. (5.3)

16
Retry only when retrying can help.

Format/structural errors → retry with the error fed back. Information absent from the source → futile; route to human or mark missing. (5.4)

17
Independent instance reviews generated work.

A model that just generated code is biased toward its own reasoning; a separate review instance with no prior context catches more. (5.6)

18
Preserve provenance via structured claim-source mappings.

Claim → source → excerpt → date as structured fields surviving summarization; annotate conflicts with both values; dates prevent temporal gaps reading as contradictions. (6.6)

19
Protect critical facts from summarization & position effects.

Exact numbers/dates in a persistent case-facts block; key findings first (counter lost-in-the-middle); trim verbose tool outputs. (6.1)

20
Subagents have isolated context; pass what they need, include "Task".

Subagents don't inherit history — pass findings in the prompt. A coordinator needs "Task" in allowedTools to delegate at all. (2.3)

The meta-rule

Find the root cause, choose the proportionate fix, match the guarantee level. Distractors love to (a) fix a different problem, (b) over-engineer — trained classifier, routing layer, bigger model — when a description/criteria/config change suffices, or (c) rely on probabilistic compliance where a deterministic guarantee is required.

10.1Master glossary

Grouped by theme. Each entry is exam-ready: what it is, and the one thing the exam expects you to know about it.

Agents, loops & orchestration
Agentic loop
The repeating cycle: send the conversation to Claude → inspect stop_reason → if tool_use, run the tool(s) and append results → loop → stop on end_turn. Control flow is driven by stop_reason, nothing else.
stop_reason
Why the model stopped. Key values: tool_use (continue the loop), end_turn (stop), max_tokens (output limit hit), refusal (declined on safety grounds).
tool_result
The block you append carrying a tool's output back to the model so it can reason about the next step. Tool results accumulate in context.
Model-driven decision-making
Claude decides which tool to call next based on context, as opposed to a pre-configured decision tree. Agentic systems favor the former.
Workflow vs. agent
A workflow follows predefined code paths; an agent lets the model direct its own steps and tool use. Start with the simplest thing that works; add autonomy only when needed.
Coordinator (orchestrator)
The hub agent that decomposes a task, decides which subagents to invoke, routes all inter-subagent communication, aggregates results, handles errors. Central to hub-and-spoke.
Subagent
A specialized agent the coordinator spawns for a sub-task. Runs with isolated context (no automatic inheritance of history); only its final result returns.
Hub-and-spoke architecture
All communication flows through the coordinator (hub), never directly between subagents (spokes). Gives observability, consistent error handling, controlled information flow.
Task tool (a.k.a. Agent tool)
The mechanism a coordinator uses to spawn a subagent. The coordinator's allowedTools must include "Task" or it cannot delegate. (Current SDKs also expose this as the Agent tool; the exam's Feb-2025 framing calls it Task.)
AgentDefinition
Configuration for a subagent type: description, system prompt, allowed tools, and (in current SDKs) model and reasoning effort.
Parallel spawning
Emitting multiple Task calls in a single coordinator response so subagents run concurrently. One-per-turn is merely sequential.
Subagent depth limit
A subagent cannot spawn its own subagents; only the top-level coordinator spawns. Reinforces the single-hub model.
Iterative refinement loop
The coordinator evaluates synthesis output for gaps, re-delegates targeted queries, and re-invokes synthesis until coverage is sufficient.
Narrow-decomposition failure
Subagents all succeed but output misses whole sub-topics because the coordinator decomposed too narrowly. The fault is upstream, not in the workers.
Enforcement, hooks & handoffs
Programmatic enforcement
Guaranteeing behavior in code (hooks, prerequisite gates) rather than prompt text. Required whenever a rule must hold deterministically — money, identity, safety.
Prompt-based guidance
Steering behavior with instructions/examples. Probabilistic — a non-zero failure rate — so insufficient for must-hold rules.
Hook
A deterministic callback at a defined lifecycle point, running in the application process at zero model-token cost. Exam-relevant: PreToolUse, PostToolUse, plus UserPromptSubmit, Stop, SubagentStart/Stop, PreCompact.
Prerequisite gate
Blocks a downstream tool call until a prerequisite step has completed — e.g. block process_refund until get_customer returns a verified ID.
Data normalization (via PostToolUse)
A hook converting heterogeneous tool outputs (Unix timestamps, ISO-8601, numeric status codes) into one consistent format before the model reasons over them.
Structured handoff
A compiled escalation summary (customer ID, root cause, amount, recommended action) handed to a human who lacks the conversation transcript.
Tools & MCP
Model Context Protocol (MCP)
An open standard (announced Nov 2024) connecting AI applications to external systems over JSON-RPC 2.0. Architecture: hosts contain clients; each client connects to a server.
MCP server primitives
Tools (model-controlled — actions), Resources (application-controlled — context/data), Prompts (user-controlled — templates). Knowing who controls which is exam gold.
MCP resource
Exposes a content catalog (issue summaries, doc hierarchies, DB schemas) so the agent has visibility without burning exploratory tool calls.
isError flag
The MCP mechanism for signaling a tool failure back to the agent within a tool result.
Structured error response
An error payload carrying errorCategory (transient/validation/business/permission), an isRetryable boolean, and a human-readable message — so the agent recovers intelligently.
Transient vs. validation vs. business vs. permission error
Transient = retry (timeout, unavailability); validation = fix input and retry; business = policy violation — don't retry, explain/escalate; permission = not allowed.
Access failure vs. valid empty result
A failed query (needs a retry decision) vs. a successful query that found nothing (no retry needed). Never conflate them.
Tool description
The primary signal for tool choice. Thin descriptions cause misrouting among similar tools; rich descriptions (purpose, input format, examples, edge cases, "use vs. similar tool" boundaries) fix it.
Tool splitting vs. consolidation
Split a vague generic tool into purpose-specific tools with clear contracts; consolidation is valid but heavier and rarely the "first step."
tool_choice
auto (may answer in text or call a tool), any (must call some tool), forced {"type":"tool","name":"…"} (must call that tool), none (may not call any tool — current APIs add this beyond the exam's listed three).
Scoped tool access (least privilege)
Give each agent only the tools its role needs. Too many tools (18 vs. 4–5) degrades selection; off-role tools get misused.
.mcp.json
Project-scoped, shared/version-controlled MCP server config. Supports ${VAR} environment-variable expansion for secrets.
~/.claude.json
User-scoped, personal/experimental MCP server config (not shared).
Built-in tools
Grep (search contents), Glob (match paths/names, e.g. **/*.test.tsx), Read/Write (full-file ops), Edit (targeted change via unique text match; fall back to Read+Write when the anchor isn't unique), Bash. Build understanding incrementally — Grep entry points → Read to follow imports — not by reading everything upfront.
Claude Code configuration
CLAUDE.md hierarchy
User-level (~/.claude/CLAUDE.md, personal), project-level (.claude/CLAUDE.md or root, shared via VCS), directory-level (subdirectory files). More-specific scopes layer onto broader ones.
@import
Pulls external files into a CLAUDE.md, keeping it modular — import only the standards relevant to each package.
.claude/rules/
Topic-specific rule files (e.g. testing.md) as an alternative to one monolithic CLAUDE.md. With YAML frontmatter paths globs, rules load only when editing matching files.
Path-scoped rule
A rule activated by glob (paths: ["**/*.test.*"]) regardless of directory — the right tool for conventions that follow scattered files.
Slash command
A reusable command. Project-scoped in .claude/commands/ (shared); user-scoped in ~/.claude/commands/ (personal). (In current Claude Code, commands and skills converged on the SKILL.md format.)
Skill / SKILL.md
An on-demand, task-specific workflow in .claude/skills/<name>/SKILL.md. Frontmatter: context: fork (isolated sub-agent), allowed-tools (restrict tools), argument-hint (prompt for missing args).
Skill vs. CLAUDE.md
Skill = on-demand, task-specific; CLAUDE.md = always-loaded, universal standards.
/memory
Shows which memory/config files are loaded — used to diagnose inconsistent behavior.
/compact
Compresses conversation context during long sessions.
Plan mode
For complex, large-scale, multi-file, architecturally significant, or multiple-valid-approach tasks: explore and design before changing code, preventing costly rework.
Direct execution
For simple, well-scoped changes — a single-file fix, one validation check.
Explore subagent
Isolates verbose discovery output and returns a summary, preserving the main conversation's context budget.
-p / --print
Non-interactive mode: process prompt → print → exit. Essential in CI so jobs don't hang waiting for input.
--output-format json / --json-schema
Enforce machine-parseable structured output in CI — e.g. to post findings as inline PR comments.
Session resumption (--resume <name>)
Continue a specific prior named conversation.
fork_session
Branch independently from a shared analysis baseline to explore divergent approaches in parallel.
Resume vs. fresh-summary
Resume when prior context is mostly valid; start fresh with an injected structured summary when prior tool results are stale (files changed since).
Prompting & structured output
Explicit criteria
Specific, categorical rules ("flag a comment only when claimed behavior contradicts actual code") beat vague guidance and beat "be conservative"/"only high-confidence."
False-positive management
High-false-positive categories erode trust in accurate categories; temporarily disable a noisy category while you fix its prompt.
Few-shot prompting
2–4 targeted, diverse examples — the most effective fix when detailed instructions still yield inconsistent output. Show reasoning on ambiguous cases so the model generalizes. Reduces hallucination and empty extractions on varied formats.
tool_use for structured output
A tool whose input schema is your target gives guaranteed schema-valid output — eliminates JSON syntax errors.
Syntax vs. semantic errors
Strict schemas remove syntax errors (malformed JSON, wrong shape) but not semantic errors (line items don't sum, value in wrong field). Semantic validation is still required.
Nullable/optional fields
Mark fields the source may lack as nullable so the model returns null instead of fabricating values.
"other" + detail / "unclear" enums
Escape hatches that keep rigid enums from forcing a wrong category on extensible or ambiguous data.
Validation-and-retry loop
On failure, resend the document + failed extraction + specific error for self-correction. Effective for format/structural errors; futile when the info is absent from the source.
Self-correction fields
Extract calculated_total beside stated_total, or add conflict_detected, to flag discrepancies rather than hide them.
Strict mode / Structured Outputs
Schema-as-grammar enforcement of output shape. The exam references strict schemas via tool use; current platforms add a dedicated Structured Outputs feature — same goal: guaranteed shape.
Batch, review & reliability
Message Batches API
~50% cheaper, up to a 24-hour processing window, no latency SLA, no multi-turn tool calling within a request. Right for overnight/weekly latency-tolerant jobs; wrong for blocking (pre-merge) workflows.
custom_id
Per-request identifier to correlate batch responses (which return out of order) and to resubmit only failed items.
Batch SLA arithmetic
Size submission cadence around the 24-hour ceiling — e.g. 4-hour windows to back a ~30-hour SLA.
Self-review limitation
A model that just generated something retains its reasoning and is less likely to question itself. Prefer an independent review instance.
Multi-pass review
Split large reviews into per-file local passes plus a cross-file integration pass to avoid attention dilution and contradictory findings. A bigger context window does not fix attention quality.
Confidence calibration
Raw model confidence is unreliable until calibrated against a labeled validation set; only then use it to route review.
Stratified random sampling
Sample within segments (e.g. high-confidence extractions) to measure true error rates and catch novel patterns an aggregate metric hides.
Context, escalation & provenance
Progressive-summarization risk
Summaries blur away exact numbers, percentages, dates, and customer-stated expectations. Avoid by keeping facts verbatim.
"Lost in the middle"
Models attend reliably to the start and end of long inputs and may drop middle content. Put key findings first; use explicit section headers.
Case-facts block
A persistent block of transactional facts (amounts, dates, order numbers, statuses) included in every prompt, kept outside summarized history.
Tool-output trimming
Strip verbose tool results to only the relevant fields (5 of 40+ order fields) before they bloat context.
Scratchpad file
A file where an agent records key findings, re-read later to counteract context degradation across boundaries.
Context degradation
In long sessions, models drift to "typical patterns" instead of the specific classes discovered earlier; counter with scratchpads, summaries, subagent isolation, /compact.
Crash-recovery manifest
Each agent exports state to a known location; the coordinator loads a manifest on resume and re-injects it.
Escalation triggers
Explicit human request (immediately, no investigation first), policy gap/exception (policy silent or ambiguous), or inability to make meaningful progress — not complexity alone.
Sentiment/self-confidence as bad proxies
Customer sentiment ≠ case complexity; self-reported confidence is uncalibrated. Use explicit criteria + few-shot instead.
Multiple-match disambiguation
When a lookup returns several matches, ask for another identifier rather than guessing heuristically.
Error propagation
Subagents handle transient failures locally; propagate only unrecoverable errors with failure type, what was attempted, and partial results. Anti-patterns: silent suppression (empty-as-success) and whole-workflow termination.
Coverage annotations
Synthesis marks which findings are well-supported vs. which topic areas have gaps from unavailable sources.
Claim-source mapping (provenance)
Structured links (claim → source URL/name → excerpt) downstream agents must preserve through synthesis, so attribution survives.
Conflict annotation
When credible sources disagree, keep both values with attribution; separate well-established from contested findings.
Temporal data
Require publication/collection dates so a time gap (2019 vs. 2024 figure) isn't misread as a contradiction.
Content-type rendering
Financial data as tables, news as prose, technical findings as lists — don't flatten everything to one format.
