01 / The Concept

A focused helper that does the digging for you.

A subagent is a specialised assistant Claude Code can hand a task to. Each one runs inside its own context window — reading files, running searches, tracing code — and when it's finished, only a clean summary returns to your main thread. Every intermediate step stays isolated, so it never clutters the conversation you actually care about.

The trade is simple and honest: you gain a pristine main context, but you give up visibility into how the answer was found. Worth it when you need the result, not the journey.

02 / Creation

Five deliberate steps with /agents.

A subagent is just a markdown file with YAML frontmatter. The /agents command walks you through building one — and the recommended path is to describe what you want and let Claude draft it.

01

Open /agents

Launch the management interface and choose “Create new agent.”

02

Choose scope

Project-level for this repo only, or user-level shared across every project.

03

Generate config

Describe the role — Claude writes the name, description and system prompt.

04

Scope the tools

Read-only, edit, execution, MCP. Grant only what the task truly needs.

05

Model & colour

Pick the engine, then a colour to identify the agent at a glance.

Haiku

Fast, lightweight tasks where speed matters most.

Sonnet

The balanced middle ground of speed and depth.

Opus

Reserved for genuinely complex analysis.

Inherit

Adopts whatever model the main conversation runs.

03 / Craft

Four patterns separate a drifting agent from a dependable one.

01

Shape the description

The main agent reads each name and description to decide when to delegate — and uses it to write the input prompt. Say “tell the agent precisely which files to review,” and the prompt becomes specific.

02

Define the output

The single most valuable improvement. A structured format creates natural stopping points and stops the agent over-researching when it can't tell that it's done.

03

Surface obstacles

Workarounds, setup quirks, special flags and tricky dependencies must appear in the summary — otherwise the main thread rediscovers them, wasting time and tokens.

04

Limit tool access

Give an agent only the tools its job requires. It prevents unintended side-effects and keeps each agent's role unmistakably clear.

A structured review, section by section.

Once every section is filled in, the agent knows it can stop — and the final “Obstacles” line ensures nothing learned is lost.

Summary — overview & overall assessment
Critical Issues — security, integrity, logic errors
Major Issues — quality, architecture, performance
Minor Issues — style, documentation, small wins
Recommendations — refactors & best practices
Approval Status — merge, or requires changes?
Obstacles Encountered — flags, workarounds, quirks

04 / Judgement

Knowing when not to delegate is the real skill.

Send them in — when it pays off

  • i.
    Research & exploration — you need the result, not a play-by-play of every file read.
  • ii.
    Code reviews — fresh eyes in a separate context, with consistent team standards.
  • iii.
    Custom system prompts — copywriting voice, or a styling agent that auto-loads your design system.

Hold them back — the anti-patterns

  • i.
    “Expert” personas — “you are a Python expert” adds nothing Claude can't already do.
  • ii.
    Sequential pipelines — when each step depends on the last, information is lost in handoff.
  • iii.
    Test runners — they hide the full output you need to debug. The worst-performing pattern in testing.
