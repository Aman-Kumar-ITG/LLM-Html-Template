Your recurring mistake patterns

Read these before any card. Most lost points reduce to one of the four shapes below.

TRAP 1 Bigger budget ≠ fix

A bigger model, larger context window, more retries or more budget never fixes a category problem: incompatibility, missing inheritance, shape-vs-semantics, or relevance. If the thing was never passed, never compatible, or never validated, scaling resources changes nothing.

TRAP 2 Prompt patch ≠ guarantee

"Add a system-prompt instruction" is probabilistic — it has a non-zero non-compliance rate on every invocation. Whenever a structural or deterministic fix exists (server-side gate, schema, scoped tools), the prompt directive is almost always the weakest option offered.

SHAPE 1 EXCEPT / FALSE stems

Three options will be true statements; you are hunting the one false one. Slow down and test each option independently against the mechanism — don't pattern-match to the first plausible-sounding line.

SHAPE 2 LEAST / weakest stems

All four options "work" to some degree; you must rank them. The prompt-only option is usually the LEAST effective; the deterministic, structural option usually wins "most effective."

THEME A

Deterministic vs probabilistic enforcement

Concept

A prompt instruction is advice the model usually follows; a server-side check is a law the system always enforces. Language models are probabilistic samplers, so any behavioral instruction — "never refund more than $500" — has a non-zero non-compliance rate per invocation, and that rate compounds across thousands of calls. A validation inside the process_refund tool implementation runs deterministically on every invocation path, including calls made by delegated subagents, retried turns, and adversarially-prompted sessions. The model can be confused, jailbroken or simply unlucky; the server cannot. Note the subtle distractor: prompts absolutely can express a numeric threshold ("$500") — expressibility is not the problem. Probabilistic adherence is the problem.

Correct design

Enforce the ceiling inside the tool/server: the refund endpoint itself rejects any amount > 500 without an approval token, returning a structured error the model can relay. The prompt may still mention the policy for UX, but the guarantee comes from code.

Why I got it wrong

TRAP 2 · prompt patch "Strengthen the system prompt" sounds responsive and is the easiest edit — but it is the weakest option whenever a deterministic alternative exists. DISTRACTOR "Prompts can't represent numeric limits" is a false rationale; reject any option justified that way. Also wrong: relying on the coordinator's prompt when subagents call the tool directly — their invocations never pass through the coordinator's instructions.

Worked example

# inside the MCP / tool server — runs on EVERY call
def process_refund(order_id, amount, approval_token=None):
    if amount > 500 and not verify_approval(approval_token):
        return {"status": "rejected",
                "reason": "amounts over $500 require manager approval"}
    return execute_refund(order_id, amount)

Self-check — Why is a system-prompt ceiling of "$500 max refunds" insufficient?

A prompt can state "$500" perfectly well — the failure is the non-zero non-compliance rate, which a server-side check eliminates.

Concept

If a workflow has hard prerequisites — "no order lookup or refund until identity is verified" — the safest expression of that rule is a gate in the execution layer, not an ordering hint in the prompt. The gate inspects session state (was get_customer called with a verified result this session?) and refuses downstream tools until the precondition holds. This converts a soft behavioral preference into an invariant that survives model confusion, prompt drift, multi-turn forgetting, and subagent delegation. The model still chooses how to converse; it simply cannot reach the consequential action out of order. Gates compose: each sensitive tool can check the specific facts it requires.

Correct design

Wrap lookup_order and process_refund in a check that a verified customer record exists in session state; return a structured "prerequisite not met: verify identity first" error otherwise. The error message itself steers the model back on track.

Why I got it wrong

TRAP 2 · prompt patch "Tell the model to always verify first" merely lowers, never zeroes, the violation rate. TRAP 1 · bigger budget A smarter model is still sampling — capability does not produce a guarantee. Tool descriptions mentioning the prerequisite are also advisory only.

Worked example

def lookup_order(order_id, session):
    if not session.get("verified_customer_id"):
        return {"error": "PREREQ_IDENTITY",
                "message": "Verify the customer before order access."}
    ...

Self-check — The strongest way to ensure refunds never run before ID verification is:

Only the execution-layer gate is deterministic; A and C are probabilistic, D is the bigger-budget trap.

Concept

The canonical support pipeline is a fixed causal chain: get_customer (verified) → lookup_order → eligibility check → process_refund. Each step's output is the next step's required input, so the ordering is not a stylistic preference — it is data dependency plus risk control. The architecture question is where the ordering is enforced. The right answer combines free conversation with a deterministic gate that blocks the financial step until all upstream facts (verified identity, real order, passing eligibility) exist in session state. This gives natural dialogue everywhere except the one place that must never go wrong.

Correct design

Let the model converse and call read-only tools flexibly, but gate process_refund on programmatically-verified prerequisites: verified identity present, order belongs to that customer, eligibility check returned true. The gate is the enforcement; the prompt is just guidance.

Why I got it wrong

TRAP 2 · prompt patch Options that "describe the ordering in the system prompt" are the weakest. Options that force every turn rigidly (e.g., tool_choice forcing) break conversation and still don't validate the data dependencies. The winner pairs flexibility with one deterministic chokepoint.

Worked example

# gate on the LAST, irreversible step
def process_refund(order_id, amount, session):
    cust = session.get("verified_customer_id")
    if not cust:                       return err("verify identity first")
    if not owns(cust, order_id):       return err("order/customer mismatch")
    if not session.get(f"elig:{order_id}"): return err("run eligibility check")
    return refund(order_id, amount)

Self-check — Where should the identity→order→eligibility→refund ordering be enforced?

One chokepoint at the irreversible action gives the guarantee while preserving natural conversation.

THEME B

tool_choice & extended thinking mechanics

Concept

Extended thinking requires the assistant turn to begin with a thinking block the model generates freely. tool_choice: "any" and tool_choice: {"type":"tool"} work by prefilling the assistant turn with the start of a tool call — which collides with the requirement that thinking come first. The API therefore returns an error when extended thinking is combined with "any" or "tool"; only "auto" (model decides) and "none" (no tools) are compatible. This is a hard API incompatibility, a category constraint — no parameter tuning, larger thinking budget, or model upgrade changes it.

Correct design

Keep thinking enabled with tool_choice: "auto", and obtain your hard guarantee where guarantees belong: a deterministic prerequisite gate in the tool layer (Theme A). You get reasoning and enforcement, without fighting the API.

Why I got it wrong

TRAP 1 · bigger budget Raising the thinking budget or swapping models cannot reconcile an incompatibility. TRAP 2 · prompt patch "Instruct it to always call the tool" with thinking on is probabilistic; the deterministic gate is the real answer. The distractor "disable thinking to force the tool" sacrifices the reasoning you were told to keep.

Worked example

{"model": "claude-sonnet-4-5",
 "thinking": {"type": "enabled", "budget_tokens": 4096},
 "tool_choice": {"type": "auto"},   // "any"/"tool" → API error
 "tools": [...]}

Self-check — You need extended thinking AND certainty a sensitive flow can't skip verification. Best config?

"any"/"tool" + thinking errors out (A); C drops thinking; D is both traps at once. B keeps thinking and gets the guarantee structurally.

Concept

When you force a tool with "any" or "tool", the API prefills the assistant turn so that it starts with a tool_use block. There is no room for the model to emit text first — so "say a friendly sentence to the customer, then call the tool" is structurally impossible in that single turn. The missing preamble is not a verbosity setting, a max_tokens issue, or a thinking side-effect; it's the prefill mechanism itself. Understanding why rules out the distractors instantly: anything that doesn't remove the prefill can't restore the text.

Correct design

Either switch to tool_choice: "auto" and instruct the model to respond with text before calling the tool, or split the work: emit the customer-facing message in one turn, then make the (forced) tool call in a separate turn.

Why I got it wrong

DISTRACTOR "Increase max_tokens" — the text isn't truncated, it was never generatable. DISTRACTOR "Disable extended thinking" — thinking is unrelated to the prefill. Both are plausible-sounding knobs that don't touch the mechanism.

Worked example

// forced: turn begins as {"type":"tool_use", ...} — no text possible
"tool_choice": {"type": "any"}
// fix: let the model speak, then call
"tool_choice": {"type": "auto"}
// system: "Briefly acknowledge the customer, then call lookup_order."

Self-check — With tool_choice "any", no greeting text ever appears before the tool call because:

It's the prefill mechanic. Fix with "auto" + instruction, or a separate message turn.

Concept

These two controls solve two different halves of one extraction problem. tool_choice: "any" guarantees the response is a tool call — never prose, never "I couldn't find a matching document type." Strict tool use guarantees the chosen tool's inputs conform exactly to its JSON schema — correct property names, types, required fields, no inventions. For a pipeline ingesting unknown document types where you define one tool per type, "any" forces the model to pick some classification tool, and strict mode makes whatever it emits machine-parseable. Either control alone leaves a gap: "auto" permits prose escapes; non-strict permits malformed payloads.

Correct design

Define one tool per document type (or one with a type enum), set tool_choice: "any", enable strict tool use, and parse with confidence downstream. (Cross-reference K3.)

Why I got it wrong

SHAPE Options offering only one of the two guarantees are partial answers. Remember the mapping: "never prose" → "any"; "never malformed" → strict. And remember what strict does NOT give you: semantic correctness (K1).

Worked example

"tool_choice": {"type": "any"},
"tools": [
  {"name": "extract_invoice", "strict": true, "input_schema": {...}},
  {"name": "extract_receipt", "strict": true, "input_schema": {...}},
  {"name": "extract_contract","strict": true, "input_schema": {...}}]

Self-check — Unknown doc types must ALWAYS yield a parseable tool call. Which pairing?

"any" removes the prose escape hatch; strict removes malformed inputs. B still allows prose; C/D guarantee nothing.

THEME C

Identity / disambiguation safety

Concept

When an identity lookup returns two plausible profiles, every automatic tie-breaker — most recent activity, shared email domain, higher lifetime value, fuzzy name similarity — is a heuristic, and heuristics are sometimes wrong. Acting on the wrong identity is uniquely dangerous because the failure is silent (nothing errors; the wrong account just gets modified) and often irreversible (a refund issued, an address changed, PII disclosed to the wrong person). The expected cost of one wrong-identity action dwarfs the friction of one clarifying question. So the canonical behavior is to stop and request a disambiguating identifier the user can supply: order number, email on file, last four digits, billing zip.

Correct design

Return both candidates' non-sensitive distinguishing facts, ask the customer for one discriminating identifier, and proceed only on an exact match. Encode this in the lookup tool's contract: an ambiguous: true status the agent must resolve before downstream calls.

Why I got it wrong

DISTRACTOR "Pick the most recently active" feels smart and usually works — "usually" is exactly the problem in a consequential, silent-failure setting. Confidence thresholds on heuristics are still heuristics. Risk asymmetry, not accuracy rate, decides this question.

Worked example

{"status": "ambiguous",
 "candidates": [
   {"id": "C-118", "hint": "j***@gmail.com, joined 2021"},
   {"id": "C-907", "hint": "j***@acme.com, joined 2024"}],
 "required": "ask user for order # or email on file"}

Self-check — Lookup returns two "Jordan Lee" profiles. The agent should:

All heuristics fail silently and possibly irreversibly on the wrong account; a clarifying question is cheap insurance.

THEME D

Context, decomposition, parallelism

Concept

When one request spans several concerns (billing, shipping, account status) for the same customer, the naive decomposition gives each concern its own end-to-end flow — and each flow re-resolves the customer's identity. That wastes calls and, worse, creates cross-concern parameter bleed: independent resolutions can land on slightly different identifiers (an old email vs. a customer ID), so the concerns silently investigate different entities. The correct decomposition factors out the shared dependency: resolve identity once, pin the canonical ID, then fan the concerns out in parallel, each receiving the same resolved identity as an explicit input. Shared facts are resolved at the layer above the fan-out, exactly like hoisting an invariant out of a loop.

Correct design

Step 1 (sequential): get_customer once → canonical ID. Step 2 (parallel): billing, shipping, account checks, each parameterized with that ID. Synthesis consumes all three.

Why I got it wrong

DISTRACTOR "Fully independent parallel flows" looks maximally parallel but triples identity calls and invites bleed. DISTRACTOR "Fully sequential everything" is safe but forfeits the latency win on genuinely independent concerns. Parallelize the independent part, share the dependent part.

Worked example

cust = get_customer(email)            # once
# same turn — parallel, all keyed to cust.id:
check_billing(cust.id) | check_shipping(cust.id) | check_account(cust.id)

Self-check — Three concerns for one customer. Best decomposition?

B removes redundant calls and the divergent-identity bug while keeping the parallel speedup.

Concept

All tool calls emitted in one assistant turn are dispatched as a set with no ordering guarantee — they may execute concurrently or in any order, and none of them can see another's result, because results only return in the next user turn as tool_result blocks. So a synthesis step that consumes four search results structurally cannot share a turn with those searches: at emission time the results don't exist. The dependency graph maps directly onto turns: independent siblings share a turn; anything downstream of a result waits for the following turn. The wall-clock math: four ~5s searches in parallel ≈ 5s, plus ~5s of synthesis in the next turn ≈ 10s total, versus ~25s fully sequential.

Correct design

Turn 1: emit all four search calls together. Turn 2: results come back; the model synthesizes. Two turns, not one and not five.

Why I got it wrong

DISTRACTOR "Emit the synthesis call fifth in the same turn — it's listed last, so it runs last." Declaration order is not execution order, and the inputs wouldn't exist anyway. Map dependency → turn boundary, always.

Worked example

Turn 1 (assistant): search(q1) search(q2) search(q3) search(q4)  # ~5s, parallel
Turn 2 (user):      4 × tool_result
Turn 2 (assistant): synthesize(...)                              # ~5s → ≈10s total

Self-check — Why can't synthesis be a fifth call in the same turn as the four searches?

Order within a turn carries no execution semantics; dependent work belongs to the turn after results return.

Concept

disable_parallel_tool_use: true constrains the model to emit at most one tool call per assistant turn. That is a cap on the count of simultaneous calls — a throttle. It does not let you choreograph the sequence of operations, does not make calls within a turn execute in declaration order (with the flag there's only ever one), and does not encode dependencies. People reach for it hoping to "make calls run in order," but ordering across operations is achieved by turn structure and by deterministic gates, not by this flag. Use it when downstream systems can't tolerate concurrency (rate limits, non-reentrant tools), not as a sequencing mechanism.

Correct design

Need serialization for safety? Use the flag. Need a specific order with data dependencies? Structure turns (D2) and gate prerequisites (A2). Different problems, different tools.

Why I got it wrong

DISTRACTOR Conflating "one at a time" with "in the order I want." The flag guarantees the former and says nothing about the latter — the model still chooses which single tool to call each turn.

Worked example

"tool_choice": {"type": "auto", "disable_parallel_tool_use": true}
# effect: ≤1 tool_use block per assistant turn. Nothing about ordering.

Self-check — disable_parallel_tool_use guarantees:

It throttles concurrency; sequencing comes from turn structure and gates.

Concept

Long sessions degrade through three distinct failure modes, and each needs its own fix — "fits in context" is not the same as "attended to." (1) Lost specifics: concrete case facts stated early stop being used → periodically re-inject a compact, current case-facts block near the end of context. (2) Position effect: material buried mid-context gets weak attention → front-load critical instructions/facts under a clearly labeled header where attention is strong. (3) Window pressure: verbose tool outputs flood the window until old content is squeezed out → trim at the source (tool returns concise summaries, server-side filtering) rather than after damage. A question describing all three symptoms wants the matched triple, not one generic remedy.

Correct design

Re-injected case-facts block + front-loading under a header + source-side trimming of tool output — each targeting its own mechanism.

Why I got it wrong

TRAP 1 · bigger budget "Use a larger context window" only delays window pressure and does nothing for attention position or fact staleness — a relevance/attention problem is a category a bigger window can't buy out of.

Worked example

## CASE FACTS (current — re-injected every N turns)
- customer: C-118 (verified)   - order: O-5521, $349
- issue: damaged on arrival    - decided: replacement approved

Self-check — Early facts ignored, mid-context rules skipped, window overflowing with tool logs. Fix?

Three mechanisms, three matched fixes. A is the budget trap; C is the prompt trap.

THEME E

Claude Code configuration

Concept

A rule file in .claude/rules/ can declare a paths glob in its frontmatter. The glob is an activation gate: the rule loads into context only when Claude is working on a file matching the pattern. Multiple globs on one rule are OR'd — matching any one activates it. Matching is against the file paths being edited, independent of which directory you launched Claude from. The recurring distractor is that globs control display order or priority — they do not; they control nothing except whether the rule is in play at all. This keeps context lean: API conventions load only when touching api/**, test rules only when touching *.test.ts.

Correct design

Scope each rule with the narrowest glob(s) that cover its domain; rely on OR semantics for multi-area rules; never expect globs to order or rank rules.

Why I got it wrong

DISTRACTOR "Globs set the order rules display in" — false. DISTRACTOR "Rules apply only when running from that directory" — activation is path-of-edited-file based, directory-independent.

Worked example

--- # .claude/rules/api-conventions.md
paths:
  - "src/api/**/*.ts"
  - "src/server/**/*.ts"   # OR — either match activates
---
All endpoints validate input with zod before handlers run.

Self-check — A rule has two paths globs. When does it load?

Globs gate activation, OR'd, directory-independent. They never set order.

Concept

Plan mode is a read-only deliberation phase: Claude explores the codebase and proposes an approach for approval before any edits. Its value is proportional to decision risk — architectural ambiguity, several competing viable approaches, changes fanning across many files. There, choosing wrong is expensive, so you plan first, get sign-off, then switch to direct execution to implement the approved plan. Concept

Three session mechanisms answer three questions about prior context. fork_session: "I want to try multiple divergent directions from the same baseline" — each fork starts from an identical snapshot and evolves independently, perfect for A/B'ing approaches. --resume: "the prior context is still mostly valid and I'm continuing the same line of work" — cheapest, keeps everything. Concept

When several mutating calls (file edits, migrations) are batched in one parallel turn, a failure in one call cancels its in-flight siblings — some mutations have landed, some were cancelled mid-flight, and you're left with partial state that's hard to even enumerate, let alone roll back. Parallel batching is a latency optimization designed for independent reads; mutations carry consistency requirements that the cancellation behavior violates. Correct design

Reads: batch freely. Risky writes: one mutation per turn, verify, proceed. Treat each write turn as a checkpointed transaction step.

Why I got it wrong

DISTRACTOR "Batch all five edits for speed" — speed is real, but the failure mode (partial, ambiguous state from sibling cancellation) is exactly what the question is probing.

BAD : Turn 1 → edit A + edit B + edit C   # B fails → C cancelled, A landed
GOOD: Turn 1 → edit A ✓ · Turn 2 → edit B ✗ stop, fix · Turn 3 → edit B ✓ …

Sibling cancellation creates un-checkpointed partial state; sequencing makes every step atomic and visible.

THEME F

Technique-to-situation matching

Concept

Three prompting/working techniques map to three distinct epistemic situations, and the exam tests the mapping. Concrete input/output examples fit when the transform is fully specified in your head but the model maps it inconsistently — examples nail down the mapping more precisely than prose ever can. Interview pattern (have Claude ask you questions before working) fits an unfamiliar domain where you can't yet name the failure modes — you don't know what to specify, so let the model elicit the requirements. Test-driven iteration (write the test suite first, iterate until green) fits a behavior-rich component with many enumerable edge cases and regression risk — the tests become the executable specification and the regression net. Diagnose the situation first: do I know the spec exactly (examples), not at all (interview), or as a list of behaviors (tests)?

Correct design

Known-but-misapplied transform → few-shot examples. Unknown unknowns → interview pattern. Enumerable behaviors + regression risk → tests first, then iterate.

Why I got it wrong

DISTRACTOR Each technique sounds universally good, so any pairing feels defensible. Anchor on the knowledge state: full spec / no spec / spec-as-behaviors. Cross-pairings (interviewing about a transform you fully know; examples for a domain you can't characterize) waste the technique's mechanism.

Worked example

"Reformat dates like these 5 samples"        → examples (spec is exact)
"Build a HIPAA intake flow — new domain"     → interview (elicit failure modes)
"Currency rounding util, 23 edge cases"      → write tests first, iterate to green

Self-check — A parser with dozens of enumerable edge cases keeps regressing as features land. Best technique?

Enumerable edge cases + regression risk is the test-driven signature: the suite is both spec and safety net.

THEME G

Multi-agent systems

Concept

Hooks are bound to the session that registers them. A coordinator's PreToolUse/PostToolUse hooks fire for the coordinator's own tool calls — they do not fire for tool calls made inside a delegated subagent's isolated run. A SubagentStop hook is not a substitute: it fires once, on the subagent's completion, not once per tool call, so it cannot replicate per-call auditing or blocking. If a guarantee must hold for every tool invocation regardless of who makes it, enforce it where every call converges — the tool/server layer — or route results through the coordinator so its hooks see them. This is the multi-agent version of A1: per-call enforcement lives below the agents.

Correct design

Audit/validation that must cover subagent calls → implement in the tool server (or via the subagent's own hooks), not the coordinator's hooks. Use SubagentStop only for completion-time actions.

Why I got it wrong

DISTRACTOR "SubagentStop replicates PostToolUse" — wrong granularity: one completion event ≠ N per-tool events. TRAP 2 "Prompt the subagent to self-report each call" is probabilistic.

Worked example

coordinator PostToolUse ──fires──▶ coordinator's calls only
subagent tool calls     ──────▶ (no coordinator hook fires)
SubagentStop            ──fires once──▶ at completion, not per call
✔ guarantee per-call → enforce in the tool server

Self-check — Every tool call (including subagents') must be logged. Where?

A misses subagent calls; B fires once per subagent, not per call; C is probabilistic; D sees everything.

Concept

Concept

Each built-in tool owns one job shape. Glob finds files by filename pattern (**/*.test.ts). THEME I

Message Batches API

Concept

Four hard facts define batch operations. (1) Capacity: a batch holds up to 10,000 requests or 32MB, whichever limit hits first — bigger jobs are chunked into multiple batches. (2) Retention: results are retained 29 days; pipelines that need them longer must copy results to durable storage promptly. (3) Expiry: processing has a 24-hour ceiling; a request that expires unprocessed is unbilled but yields no result — it must be resubmitted, so your pipeline needs expiry handling, not just error handling. (4) Notification: there is no completion webhook — you poll the batch's processing status. Each fact is a favorite exam distractor in negated form ("a webhook fires," "expired requests are billed," "results persist indefinitely").

Correct design

Chunk to ≤10k/32MB; poll status on a backoff schedule; on end, copy results out within the 29-day window; detect expired requests and resubmit them.

Why I got it wrong

SHAPE 1 · FALSE stems These appear as "all true EXCEPT" questions. Memorize the four numbers/absences as a unit: 10k / 32MB / 29d / 24h / poll-not-push / expired-unbilled-but-resubmit.

Worked example

POST /v1/messages/batches            # ≤10,000 reqs or 32MB
GET  /v1/messages/batches/{id}       # POLL: in_progress → ended
GET  …/results                       # stream; copy out — 29-day retention
# request expired at 24h → not billed, no result → resubmit

Self-check — Which statement about the Batches API is FALSE?

No webhook exists — completion is discovered by polling. A–C are the true constraints.

Concept

To run a recurring large workload against a deadline (e.g., results by 9am daily), design around the 24-hour processing window rather than hoping. Submit in periodic windows sized so that even worst-case (full 24h) processing lands inside the SLA — e.g., submit yesterday's accumulated documents at 8am for a next-morning deadline. Correlate by custom_id: results return in arbitrary order, so each request carries your stable identifier for joining back to source records. Resubmit only the failures/expired — never the whole batch — and chunk oversized requests that errored on size. Together: predictable landing time, exact correlation, minimal redo cost.

Correct design

Window submissions against the 24h ceiling; key every request with custom_id; sweep results for errored/expired items and resubmit just those, splitting any oversize offenders.

Why I got it wrong

DISTRACTOR "Resubmit the entire batch if anything failed" — pays full cost again and risks blowing the window. "Match results by position/order" — order is not guaranteed; only custom_id is safe.

Worked example

{"custom_id": "doc-2026-06-11-00042",
 "params": {"model": "claude-sonnet-4-5", "max_tokens": 1024,
            "messages": [...]}}
# nightly: submit 08:00 → poll → join on custom_id → resubmit failures only

Self-check — 80k docs/day, results due 9am. Strategy?

B is the full pattern. A breaks correlation and the 10k cap; C forfeits batch economics; D's webhook doesn't exist.

Concept

Each batch request is a single, self-contained generation: the model produces one response and the request ends. Multi-turn tool calling requires a loop — model emits tool_use, your code executes the tool, you send the result back, the model continues. The Batches API has no mechanism to execute your tools mid-request and feed results back in; nobody is on the other end of the loop. So a workload that needs mid-analysis tool calls (e.g., a code review that must query a ticket system while reasoning) is category-incompatible with batching and must stay synchronous. (Requests can include tools and may return a tool_use as the final output — but the interactive loop cannot continue inside the batch.)

Correct design

Split the pipeline: batchable single-shot stages (classification, summarization) go to Batches; the tool-looping stage runs synchronously. Or pre-fetch tool data and inline it so the batch request needs no live calls.

Why I got it wrong

TRAP 1 · category No retry count, batch size, or model upgrade adds an execution loop that the API shape doesn't have. Incompatibility questions are settled by mechanism, not by knobs.

Worked example

batchable : "summarize this PR diff"                  # one shot
NOT       : "review this PR; query Jira for the
             linked ticket while analyzing"            # needs mid-run loop → sync

Self-check — Why can't a review needing mid-analysis Jira lookups run via Batches?

The interactive execute-and-continue loop is structurally absent; such workloads stay synchronous.

THEME J

CI / automated review design

Concept

Match the orchestration pattern to the task's structure. Three fixed, known review aspects — security, performance, correctness — are a static checklist, and the natural fit is prompt chaining: fixed sequential passes, one focused prompt per aspect, each pass getting full attention on its concern. Consensus-of-three independent passes is the wrong instrument here: consensus keeps what reviewers agree on, so a real security flaw caught by only one pass is voted away — it suppresses exactly the rare, single-detector findings reviews exist to surface. Dynamic decomposition (agent decides sub-tasks at runtime) suits open-ended investigation where aspects aren't known in advance; for a fixed list it adds nondeterminism without benefit.

Correct design

Chain: pass 1 security → pass 2 performance → pass 3 correctness; merge the three structured finding lists (union, never intersection).

Why I got it wrong

DISTRACTOR "Three independent reviews + majority vote = more reliable" — voting is for suppressing noise on the same question; findings are unions of different questions. Mis-applied reliability intuition.

Worked example

findings = []
for aspect in ["security", "performance", "correctness"]:
    findings += review(diff, prompt=PROMPTS[aspect])   # UNION of passes

Self-check — Why is consensus-of-three wrong for the three fixed review aspects?

Reviews want the union of findings; consensus computes the intersection. Chaining one focused pass per aspect fits the fixed list.

Concept

Defects shipped under confident "clean" verdicts mean the model's self-reported confidence is miscalibrated — its 0.9 doesn't correspond to 90% empirical correctness. Raw miscalibrated numbers can't be fixed by moving the threshold up or inverting it: you'd be re-slicing a distorted scale, with no idea what any cutoff means. The repair is empirical: score the reviewer against a labeled validation set (changes with known defect outcomes), learn the mapping from self-reported to actual reliability, and threshold on the calibrated value. And because calibration is imperfect and drifts, keep a human gate on consequential merges. Discarding the signal entirely wastes real (if warped) information.

Correct design

Build a labeled set → measure empirical precision per confidence band → threshold on calibrated confidence → human approval remains mandatory for high-impact merges.

Why I got it wrong

DISTRACTOR "Just require 0.95 instead of 0.8" — an uncalibrated 0.95 is as meaningless as an uncalibrated 0.8. The flaw is the scale, not the cutoff.

Worked example

band 0.9–1.0 → empirically 71% clean   # calibration table from labeled set
band 0.7–0.9 → empirically 64% clean
policy: auto-pass only calibrated ≥0.95 AND non-critical path;
        everything consequential → human gate

Self-check — Confident "clean" verdicts keep shipping defects. Best response?

Only calibration gives the numbers meaning; A/B re-slice a distorted scale, D discards usable signal.

Concept

One review category fires too often and devs dismiss it; you need to learn why it misfires. That requires the dismissal data to be analyzable, which requires structure at the point of detection: add a detected_pattern field to every structured finding, recording the specific code construct that triggered it. Now dismissals group cleanly — "84% of dismissed findings triggered on builder-pattern chaining" — and the fix designs itself. The alternatives fail the analyzability test: free-text reasons don't aggregate; demoting severity hides the noise instead of explaining it; running three times and keeping repeats filters stochastic noise but a systematic false-positive pattern reproduces consistently and sails through.

Correct design

Extend the finding schema with detected_pattern (and keep dismissal status); aggregate dismissals by pattern; refine or special-case the top offending patterns.

Why I got it wrong

DISTRACTOR "Triple-run and keep only repeated findings" sounds statistical — but systematic misfires are deterministic; repetition-filtering measures variance, not validity.

Worked example

{"category": "resource-leak", "file": "db.ts", "line": 88,
 "detected_pattern": "connection created in try without finally",
 "dismissed": true}
# GROUP BY detected_pattern WHERE dismissed → top misfiring constructs

Self-check — To analyze WHY a category misfires, the pipeline should:

Only structured trigger data aggregates into a diagnosis; B doesn't aggregate, C hides, D misses systematic (consistent) false positives.

THEME K

Structured data extraction

Concept

Strict tool use and native Structured Outputs constrain generation so the result always parses: correct property names, correct types, required fields present, no extras. That is the entire guarantee — shape and type. They cannot guarantee the content is right: a line-items array can sum to 4,210 while total says 4,580 (failed arithmetic reconciliation), or the shipping fee can land in the tax field (wrong field placement) — both are perfectly schema-valid. Semantic correctness needs a second layer: semantic validation. A strong pattern is making the model do the reconciliation explicitly — extract calculated_total (its own sum of line items) alongside stated_total (what the document says) plus a conflict_detected flag, then verify the arithmetic in code.

Correct design

Schema enforcement for shape + post-extraction semantic checks in code (cross-field arithmetic, referential sanity) + reconciliation fields in the schema itself.

Why I got it wrong

TRAP 1 · shape-vs-semantics "It's schema-validated, so the data is correct" conflates two categories. Schema validity says it parses; only validation says it's true.

Worked example

{"line_items": [...],
 "stated_total": 4580.00,
 "calculated_total": 4210.00,     # model's own sum
 "conflict_detected": true}       # + code re-verifies the sum

Self-check — Strict tool use is on, yet invoice totals don't match their line items. Why?

A wrong-but-well-typed number is schema-valid. Add calculated_total / stated_total / conflict_detected plus code-side checks.

Concept

The structured-outputs grammar enforces structural JSON-Schema features — types, required, enums, property names — but numeric minimum/maximum bounds are not enforced by the constrained-decoding grammar. A field declared 0 ≤ x ≤ 100 can still come back as 250: well-typed, out of range. So range integrity is your job: post-response validation in code rejects or flags out-of-bounds values, and you should also document the bound in the field's description — that nudges the model toward compliance (probabilistically) while the code check provides the guarantee. Notice this is Theme A in miniature: description = prompt-level advice; validator = deterministic enforcement.

Correct design

Keep the bound in the schema description for guidance + enforce it in a post-response validator that routes violations to retry or review.

Why I got it wrong

DISTRACTOR "The schema says max 100, so values are capped" — assumes the grammar enforces every keyword; it enforces structure, not numeric ranges.

Worked example

"discount_pct": {"type": "number",
  "description": "Percentage 0–100. Never exceed 100."}
# code:
if not (0 <= out["discount_pct"] <= 100): flag_for_review(out)

Self-check — discount_pct has maximum: 100 in the schema, yet 250 appears. Why, and what's the fix?

Types are enforced, ranges are not; the deterministic check lives in your code.

Concept

The extraction-pipeline framing of B3. Inbound documents of unknown type must always produce machine-actionable output. Two failure routes exist: the model answers in prose ("This appears to be a receipt…") or it calls a tool with malformed inputs. tool_choice: "any" closes the first route — the response must be one of your tools, so classification happens by tool selection itself. Strict tool use closes the second — emitted inputs match the selected schema exactly. Together, every document yields a typed, parseable record naming its own type. Keep K1 in mind even here: the output will parse; whether the extracted values are semantically right still needs validation.

Correct design

One strict tool per document type, tool_choice: "any", downstream dispatch on which tool was called.

Why I got it wrong

DISTRACTOR "auto + a 'respond only in JSON' instruction" — both halves probabilistic: prose escapes possible, malformed JSON possible. The deterministic pairing exists; use it.

Worked example

"tool_choice": {"type": "any"}
tools: extract_invoice | extract_receipt | extract_po   # all strict: true
# response tool name == document classification

Self-check — Mixed unknown docs, output must always be parseable + typed. Config?

A is the only deterministic pairing; B/C are prompt-trap variants; D parses but carries no typed structure.

Concept

Enum drift — "SALES", "Sales inquiry", an invented "partnerships" — happens when reality doesn't fit the enum and the model improvises. The durable fix changes the enum so improvisation is never necessary: add an "other" member paired with a free-text detail string (legitimate out-of-taxonomy cases get a home without corrupting the category field) and an "unclear" member (ambiguity gets an honest label instead of a guess). Then validate every return against the allowed set in code, rejecting or routing violations. Prompt pleas ("use ONLY these values") and temperature tweaks merely lower the drift rate; they guarantee nothing — membership is guaranteed by escape valves plus a validator (and strict mode does enforce enum membership at generation time; the design problem is making the enum adequate).

Correct design

Enum = real categories + other (with required other_detail) + unclear; code-side membership validation; periodic review of other_detail values to evolve the taxonomy.

Why I got it wrong

TRAP 2 · prompt patch "Strengthen the instruction to stick to the list" — drift is pressure from unrepresentable inputs; relieve the pressure structurally.

Worked example

"category": {"enum": ["sales","support","billing","other","unclear"]},
"other_detail": {"type": "string"}
# code: assert out["category"] in ALLOWED

Self-check — The model keeps inventing category values. Robust fix?

Escape valves remove the pressure to invent; validation guarantees membership. A/B reduce odds only; C abandons the taxonomy.

Concept

Sources write dates as "03/04/2025", "4 March 2025", "2025-03-04" — and your schema wants one canonical representation. The schema (even with a format hint) defines the target; it doesn't teach the mapping, especially ambiguity policy (is 03/04 March 4th or April 3rd?). The fix pairs both layers: explicit format-normalization rules in the prompt — target format, ambiguity resolution (e.g., "ambiguous numeric dates are DD/MM for EU-sourced docs"), examples of each source style — alongside the strict schema that locks the output shape. The rejected options each lose something: nullable hides perfectly parseable dates as null; free text abandons the schema; a permissive regex pattern accepts and stores the inconsistency you were trying to eliminate.

Correct design

Prompt: "Normalize all dates to YYYY-MM-DD; interpret ambiguous numeric dates as DD/MM; examples: …" + strict schema field expecting the canonical form + a code-side format check.

Why I got it wrong

DISTRACTOR "Loosen the pattern to accept any date-like string" — that imports the chaos into your database. Canonicalize at extraction, not after.

Worked example

prompt: "Dates → YYYY-MM-DD. '4 March 2025' → 2025-03-04.
         Ambiguous nn/nn: treat as DD/MM. If no date exists → null."
schema: "invoice_date": {"type": ["string","null"],
         "description": "YYYY-MM-DD"}

Self-check — Many source date styles, one canonical target. Best approach?

The prompt teaches the mapping; the schema locks the shape. A discards data, C drops structure, D stores the inconsistency.

Concept

A required field the model must always fill, on documents where the value is absent 40% of the time, creates structural pressure: the schema demands a value, the document has none, so the model fabricates a plausible PO number. The fabrication is a symptom of the schema contradicting reality. Fix the contradiction: make the field optional/nullable, so "absent" has a legal, honest representation — null — and the pressure disappears. The alternatives miss the mechanism: a required field with a sentinel like "NONE" still forces generation and the model may "helpfully" find a number anyway; a stricter regex pattern shapes the fabrication rather than preventing it; a prompt plea ("never invent values") fights structural pressure with probabilistic words.

Correct design

"po_number": {"type": ["string","null"]} + description: "null when no PO number appears in the document." Downstream treats null as a first-class state.

Why I got it wrong

TRAP 2 · prompt patch The "instruct it not to fabricate" option fails because the schema keeps demanding what the document doesn't have. Remove the demand, remove the fabrication.

Worked example

BAD : "po_number": {"type": "string"}, required        # forces invention 40% of the time
GOOD: "po_number": {"type": ["string","null"],
       "description": "PO number, or null if absent"}

Self-check — PO numbers absent in 40% of docs; the model invents them. Root fix?

Fabrication is schema pressure; nullability gives absence an honest representation. A still forces output, B shapes lies, D is the prompt trap.

Concept

Scarce human review should go where error risk is highest — and that risk has two independent sources. The model's low confidence catches cases where it knows it's unsure. But source-document ambiguity — internally contradictory totals, conflicting dates, illegible regions — is a risk the confidence score doesn't reliably capture: the model can read an ambiguous document, resolve the contradiction arbitrarily, and report high confidence in its arbitrary resolution. So the routing predicate is a union: review extractions with low confidence AND ALSO extractions whose source was flagged ambiguous or self-contradictory (detectable via cross-field checks like K1's reconciliation, or an explicit document-quality flag). Confidence-only routing systematically misses the second class.

Correct design

Queue = {confidence < τ} ∪ {source flagged ambiguous/contradictory}. Emit an ambiguity flag during extraction; compute contradiction flags in validation.

Why I got it wrong

DISTRACTOR "Low confidence alone is the efficient filter" — efficient at catching known unknowns only; confidently-wrong-on-ambiguous-input is the failure class it can't see.

Worked example

route_to_human = (out.confidence < 0.7) \
              or out.source_flags.ambiguous \
              or out.conflict_detected        # e.g. totals disagree

Self-check — Why route ambiguous-source extractions to review even at high confidence?

The two risk signals are independent; route on the union, not confidence alone.

Concept

A 98% aggregate accuracy can coexist with 60% on handwritten documents — if handwritten is a small share of volume, its failures barely dent the average. Reducing human review based on the aggregate would silently expose exactly the weakest segment. Before any review reduction, stratify validation per document type and per field: typed invoices vs scans vs handwritten; totals vs dates vs line items. Decisions then attach to the stratum: keep full review on handwritten until it independently clears the bar; relax review on segments that earn it. This is Simpson's-paradox hygiene applied to extraction QA — the aggregate is a weighted blend that can mask any minority segment's collapse.

Correct design

Validation report = accuracy matrix (doc type × field); per-stratum thresholds gate per-stratum review policy; aggregate is reported but never used as the gate.

Why I got it wrong

DISTRACTOR "98% overall clears our 95% bar — reduce review across the board." The bar must be cleared per segment the policy will apply to.

Worked example

typed PDFs    99.1%  ✓ relax review
scanned       96.4%  ✓ relax review
handwritten   60.2%  ✗ KEEP full review   # invisible in the 98% aggregate

Self-check — 98% aggregate accuracy. Before cutting review, you should:

Aggregates are blends; policy must follow per-stratum evidence.

Concept

A batch of 100,000 documents amplifies whatever configuration you submit — including its flaws — by 100,000. The professional sequence: refine prompt and schema on a representative sample (covering every document type and edge case in realistic proportions), iterate until first-pass success is high, and only then run the full batch with the proven configuration. Submitting at scale first and "fixing issues as they appear" pays for the same mistakes a hundred thousand times, burns part of the 24-hour window on doomed requests, and floods you with failures whose remediation is itself a batch-scale project. Sample-first converts an expensive open-loop gamble into a cheap closed-loop iteration — the batch should be the victory lap, not the experiment.

Correct design

Stratified sample (~200–1,000 docs) → measure per-type accuracy (K8) → fix prompt/schema → repeat until stable → submit 100k with the frozen config → spot-check results.

Why I got it wrong

DISTRACTOR "Batches are cheap — just run it and resubmit failures" — failure cost isn't only tokens: it's the SLA window, triage labor, and silent semantic errors (K1) that no resubmission loop catches.

Worked example

sample 500 (stratified) → 81% first-pass → fix date rules (K5),
nullable PO (K6), enum valves (K4) → 97.5% → freeze config
→ submit 100,000 → spot-check per stratum

Self-check — Right before a 100k-document extraction batch, the key step is:

Iterate cheaply at sample scale; submit at full scale only what's proven. A is logistics, not validation; B pays for mistakes 100,000×.
